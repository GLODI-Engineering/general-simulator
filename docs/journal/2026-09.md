## 2026-09-22 09:03 — checkpoint and resume a transient run

[#12](https://github.com/GLODI-Engineering/general-simulator/issues/12). The natural next
step after `ic=` on every stateful element and block: `ic=` is for an operating point you
*know*, a checkpoint is for one you can only reach by simulating.

**Inventory first.** Nothing in the workspace was serializable (`serde` was not a dependency
anywhere), so this is a new capability, not a gap in one. What the loop carries between
accepted steps, and therefore what a checkpoint must hold: $x_k$, $x_{k-1}$, the previous
operating point's diode segments and Norton currents, gate states, the ringing cooldown,
`prev_outputs`, the adaptive controller's `dt_next`, the loop's own `step_index` (so the resumed
first step is not forced to backward Euler), and every `BlockState`. Escape hatches: `pyblock`
state is a Python object (pickle is the same contract as the `deepcopy` clone it already
requires); `cscript` state is an opaque C heap object and `octblock` state lives inside the
`octave-cli` child — neither readable from here.

**What landed.**

- `dae-runtime/src/checkpoint.rs`: `Checkpoint`, `BlockSnapshot`, a `GSCK` + version + postcard
  file encoding (`f64` bit-exact), and a hand-rolled FNV-1a `deck_hash` over the `Debug`
  rendering of statements/dialect/blocks/models — deliberately not `DefaultHasher`, which is not
  stable across Rust versions and would make files toolchain-specific.
- `simulate_transient_with_blocks_checkpointed` takes a `CheckpointControl { resume, every,
  on_checkpoint, final_snapshot }`; the old streamed function is a wrapper passing the default.
  The `snapshot` closure and `restore_block_states` are a mirror pair. `cscript`/`octblock` are
  refused lazily, at the first snapshot, as `CheckpointUnsupportedBlock` — the first cut
  returned a final snapshot unconditionally and broke every `cscript` CLI test, hence
  `final_snapshot` is opt-in.
- `PyBlockInstance::pickle_state` / `restore_state` in `pyblock-ffi`.
- CLI: `--checkpoint-out`, `--checkpoint-every T` (write-then-rename, so a kill mid-write
  never leaves a truncated file), `--resume`. `--tfinal` stays absolute. Checkpointing forces
  the block-graph path even for a switch-free, block-free deck.

**Verification** — the defining property is bit-identity, `==` on every `f64`, never a
tolerance:

- `crates/dae-runtime/tests/checkpoint_resume.rs`: a PWM-driven buck with an ideal switch, a
  freewheeling ideal diode, a PI loop on a `prev:`-referenced measurement and one of every
  stateful block kind. Run to $T$, checkpoint through bytes, resume to $2T$: identical to the
  single run, fixed-step. Adaptive: identical when resumed from a *periodic* checkpoint. The
  test also asserts the diode changed segment and the switch toggled, so it cannot pass on a
  deck that never exercised the mode bookkeeping. Plus: deck mismatch refused, resume past
  `t_final` is an empty run, no snapshot when none asked, `pyblock` round-trips through pickle.
- `crates/general-simulator-cli/tests/checkpoint_cli.rs`: the split CSV is byte for byte the
  whole CSV (1500 rows); a periodic file left on disk resumes; edited deck refused;
  `--checkpoint-every` without `--checkpoint-out` rejected.
- Gates: fmt, clippy `-D warnings` with and without `python`, 288 workspace tests (the three
  `cscript-ffi` failures under the parallel runner are #6 and pass with `--test-threads=1`),
  both books build.

**One honest caveat, documented in the user guide.** An adaptive run's final step is clamped to
land on `t_final`, a point the uninterrupted run never stepped to; resuming from a *final*
adaptive checkpoint is an exact continuation of the saved state but follows a different, equally
valid step sequence from there. Bit-identity under adaptive stepping holds for periodic
checkpoints, which are taken after ordinary accepted steps.

**Follow-up:** the `cscript` (`cscript_state_size`/`_write`/`_read`) and `octblock`
(`save -binary`/`load`) opt-in contracts.

## 2026-09-21 20:52 — initial conditions on signal-domain blocks (`ic=`, `y0=`)

[#8](https://github.com/GLODI-Engineering/general-simulator/issues/8), with the parsing half in
[general-mna#8](https://github.com/GLODI-Engineering/general-mna/issues/8).

**The request, and what checking it found.** "Initial conditions are probably already there for
`L`/`C` but not for the signal domain" — confirmed on both counts by running the CLI, not by
reading code. `C1 b 0 1e-6 ic=5` starts at $V(b) = 5.0495$ after one 10 µs step (the hand-derived
backward-Euler value), and `wibble=5` on the same card is now rejected, so #1 and #2 here are
both fixed and only still open on GitHub. On the signal side,
`G kind=tf in=STEP num=[1] den=[1,1] ic=[0.5]` ran and started at zero: every stateful block's
state was hard-coded to rest in `simulate_transient_with_blocks_streamed`'s construction loop.

**What changed here.**

- `continuous-blocks`: `TransferFunction::settled_state(y0)` and `settled_state_discrete(y0)`,
  plus `SettledStateError`. In controllable canonical form a continuous equilibrium is
  $x = (x_1, 0, \dots, 0)$ with $x_1 = y_0 / N(0)$; a discrete one has every state equal to
  $y_0 / N(1)$. Neither needs $a_0 \ne 0$, so a pole at the origin works and the holding input is
  zero — which is exactly the meaning `kind=pid`'s `ic=` wants (output held at zero error), so the
  PID reuses the same function on its own transfer function rather than growing a second rule.
  Each test checks the result is a genuine equilibrium / fixed point of the realization
  (`derivative == 0`, `discrete_step(x) == x`) at the requested output, not just the formula.
- `dae-runtime`: the construction loop reads `BlockInstance::ic` through one `initial_state(n)`
  closure for every stateful kind. `general-mna` has already resolved and validated the vector;
  the length is re-checked only because a block can be hand-built
  (`DaeError::BlockInitialConditionLength`). Discrete blocks also seed `last_output` from the
  declared state, so a block started settled with a nonzero sample `offset` does not glitch
  through zero before its first hit.
- `BlockInstance` gained a field, so all 128 struct literals across this workspace's tests took a
  mechanical `ic: None`.

**Verification.** `crates/dae-runtime/tests/block_initial_conditions.rs` drives real netlist text
through `build_system` and the block loop, each expectation a closed form chosen so a start from
rest lands visibly elsewhere: $1 - 0.5e^{-t}$ for a first-order lag, $\cos t$ for an undriven
oscillator, $0.8 + 0.3t$ for a pre-loaded PI under constant error, $8 \cdot 0.5^k$ for a discrete
decay, $0.25 + 100t \pmod 1$ for a VCO, a torque-free PMSM coasting at its declared speed, and
both `y0=` cases held exactly at their equilibria. 28 new `doc-verify/` fixtures across 14 kinds
back every new Parameters/Errors claim against the release CLI. Gates: fmt, clippy `-D warnings`,
269 workspace tests, every `doc-verify` suite, `mdbook build book/user-guide` (no KaTeX errors).

**Found and not fixed — worth their own issues.**

- Unknown fields on a `kind=` block are silently ignored in general (`wibble=3` on a `tf`
  parses); only `ic=`/`y0=` are now policed. Issue #1 assumed the block parser was the strict
  half; for unknown keys it is not.
- A `.IC V(node)=...` directive is accepted and discarded — and `general-simulator-gui`'s netlist
  writer emits exactly that for node initial conditions, so a GUI-set node IC currently does
  nothing. Its per-element `IC=` (uppercase) does work.
- `general-mna`'s CI is red on every branch including `main`: the runner has no sibling checkout
  for the `continuous-blocks`/`pwl-devices` path dependencies.

## 2026-09-11 06:29 — follow `general-mna`'s `ic=` solve -> assignment, and test the seam end to end

[#4](https://github.com/Elvis-codeur/general-simulator/issues/4) here, following
[general-mna#5](https://github.com/Elvis-codeur/general-mna/issues/5).

**What changed upstream.** `general-mna`'s `MnaSystem::initial_state` no longer solves a
constrained operating point around the declared `ic=` values (capacitor held as an ideal voltage
source, inductor as a current source, `ic`-free storage opened or shorted). It *assigns*: an
`ic`-bearing inductor's own branch current and an `ic`-bearing capacitor's node-voltage
difference take their declared values, every other unknown starts at rest, and `A`/`K`/`B`/`u`
are untouched. That is what "use initial conditions" means — the operating point is skipped, not
solved around the declaration.

**What changed here.** No code: `resolve_initial_state` still asks the same question and gets a
better answer. What changed is what the two doc comments claim, which had become exactly
backwards. `resolve_initial_state` said the values were honored "rather than merely assigning
the declared numbers"; `DaeError::InitialCondition` described the old solve's two failure modes
(contradictory conditions, or a node with no DC path once storage is opened or shorted), neither
of which exists any more. The new failure modes are conditions that contradict *each other* and
an assignment that violates a circuit equation in which every unknown is already fixed.

`resolve_initial_state` now also says out loud that a seeded vector is **not** a consistent
operating point. That is fine here and was already anticipated — `simulate_transient` takes its
first step with backward Euler precisely because an arbitrary `x_initial` need not satisfy the
algebraic constraints, and that first step is what re-imposes them — but it was left implicit,
and the next reader would have had to re-derive it.

**New test, `crates/dae-runtime/tests/netlist_initial_conditions.rs`.** There was no end-to-end
proof that a netlist's own `ic=` reaches a transient run at all; every existing test hands over
an explicit `x_initial` or starts from rest. Five now, each expected number derived by hand from
the first backward-Euler step before the test was run, not read off a previous run:

- `V1 a 0 10` / `R1 a b 1k` / `C1 b 0 1u ic=5`, one `dt = 10 us` step. Node `b`'s KCL gives
  `V(b) = (V(a)/R + C*V(b0)/dt)/(1/R + C/dt) = 0.51/0.101 = 5.049504950495050 V`. Starting from
  rest instead gives `0.0990099...`, two orders of magnitude away, so it cannot pass by accident.
- `V1 a 0 10` / `L1 a b 5u ic=12` / `R1 b 0 10`, one `dt = 10 ns` step:
  `10 - 10 i = 500(i - 12)` gives `i = 6010/510 = 11.784313725490196 A` and `V(b) = +117.84 V`.
  The positive `V(b)` is the sign convention under test: `ic` is the current from the card's
  first node to its second, so the 12 A arrive at `b` and leave through R1.
- The same deck written `L1 b a`, where `I(L1)` keeps its number and `V(b)` goes negative —
  which is exactly why the convention is documented rather than inferred.
- An explicit all-zero `x_initial` still overriding the netlist's `ic=`, step for step against
  the same deck with the `ic=` removed.
- An `ic` on a capacitor wired across an ideal voltage source surfacing as
  `DaeError::InitialCondition`, with `I(V1)` — the violated equation — named in the message.

**Documentation.** `book/user-guide/src/netlist-grammar.md` is still the unwritten skeleton the
entry below flagged; it now carries two outline bullets for `ic=` (both sign conventions, and
the assignment semantics stated plainly) and for per-letter device-card parameter checking, so
whoever writes that chapter does not have to rediscover what belongs in it. The `doc-verify/`
suites cover `kind=` block documentation and none of them declare `ic=` or exercise a device
card's positional grammar, so none needed changing — they were all run anyway.

**Gate.** `cargo fmt --all -- --check`, `cargo clippy --all-targets -- -D warnings`, and
`cargo test --workspace` (57 test binaries, 0 failures) all green, plus every `doc-verify`
suite (35 of them, 0 failures) against a freshly built
`cargo build --release -p general-simulator-cli --features python`.

**Observed flake, unrelated.** `cscript-ffi`'s `two_instances_of_the_same_library_keep_independent_state`
failed once during a `cargo test --workspace` run that was also compiling, then passed on three
consecutive isolated runs and on two consecutive full workspace runs. Nothing in this change
touches FFI; recording it here rather than silently re-running until green, because the next
person to see it should know it has been seen before.

## 2026-09-11 05:49 — honor a netlist's own `ic=` initial conditions instead of always starting from rest

Companion to `general-mna`'s own entry at the same timestamp (that repo's #2/#3, filed from this
repo's #1/#2). The device-card parsing and the `ic=` operating-point solve both belong in
`general-mna`; this repo's share is one seam.

**What changed.** `dae_runtime::resolve_initial_state` (new, in `crates/dae-runtime/src/lib.rs`)

failing that, `MnaSystem::initial_state` honors whatever `ic=` the netlist declares; failing
that, rest, exactly as before. The `ic=` operating point is evaluated at `t = 0` with every
diode at its own off-segment reference slope and zero Norton current, matching how `solve_step`

All four places that used to write `match x_initial { Some(x) => ..., None => vec![0.0; ...] }`

**Verification.** `cargo fmt --all -- --check`, `cargo clippy --all-targets -- -D warnings`, and
`cargo test --workspace` all green, no test changes needed — every existing netlist declares no

**Remaining.** `book/user-guide/src/netlist-grammar.md` is still an unwritten skeleton, so `ic=`

## 2026-09-04 16:44 — `kind=sig2phys` wired into the netlist as a node: the silent `V(...) = 0`, now a build-time error

A `converter.sig2phys` block wired via an ordinary physical-network wire into a resistor
terminal compiled and ran without complaint and reported `V(<converter>) = 0`, while the
converter's own signal-domain output column showed the correct non-zero value on the same row.
Flagged incidentally by an earlier `gsim-core` session; root-caused and fixed here.

**Root cause (confirmed by direct reproduction, not inferred).** Minimal repro:

```
CMD  kind=const value=5
VDRV kind=sig2phys domain=voltage in=CMD
R1   VDRV 0 1k
```

produced `t,V(VDRV),CMD,VDRV` → `5e-5,0,5,5` — exit 0, in `--mode transient` *and* `--mode dc`.

Block names and circuit node names are two entirely separate namespaces that never meet. A
`BlockKind::Sig2Phys` block has no terminals and stamps **nothing** into the MNA system; it is
purely a named Signal-to-PS value that another *statement* substitutes (a `V`/`I` source's own
value field, an ideal switch's `gate=`/`ctrl=`). So a net that happens to share a converter's
name is just an ordinary node, driven by nothing. It is not singular either — `R1` to ground
gives it a perfectly well-conditioned KCL row `G·v = 0`, whose unique solution is `v = 0`. The
solve therefore *succeeds*, and the run is wrong rather than failed. Nothing in the pipeline had
any reason to notice: `general-mna` never sees the two namespaces in one place (with
`--devices <file>` the block declarations and the netlist are literally different sources), and
`dae-runtime`'s existing Signal-to-PS enforcement only inspected *symbols in a source's value
field*, never node tokens.

**Legal consumers of a `Sig2Phys`, verified against source, correcting two prior assumptions.**
(1) A *signal*-controlled voltage/current source already exists — it just isn't a distinct
device. It is an ordinary independent `V`/`I` source whose literal value field names a converter
(`V1 a 0 VDRV`), enforced by `DaeError::SourceNotSig2PhysicalConverter`. Together with an ideal
switch's `gate=`/`ctrl=` (`DaeError::GateTargetNotSig2Voltage`) those are the only two
consumers, and **both are by name, never by wire**. (2) The classic SPICE dependent sources
also all exist and are properly stamped in `general-mna` — `builder.rs`'s `stamp_vcvs` (`E`),
`stamp_vccs` (`G`), `stamp_cccs` (`F`), `stamp_ccvs` (`H`) — verified end to end
(`E1 out 0 in 0 3` over a 2 V input gives `V(out) = 6` exactly). Those are controlled by a
circuit quantity (a node pair or a named branch), never by a block, so they are not an
alternative Signal-to-PS boundary; but a dependent source's *controlling* node pair is still a
node list, so wiring a converter there (`E1 out 0 VDRV 0 3`) is caught by the same check, naming
`E1`.

**What changed (this repo only — `general-mna` needed no change).**
- `crates/dae-runtime/src/lib.rs`: new `DaeError::Sig2PhysUsedAsCircuitNode { block, element,
  node }`.
- `crates/dae-runtime/src/block_graph.rs`: new public
  `reject_sig2phys_wired_into_circuit(statements, blocks)`, called from
  `simulate_transient_with_blocks_streamed` immediately after `parse_and_flatten` and
  `block_index_by_name`, before the gate checks and before any system is built. It takes the
  *flattened* statements, so a converter wired inside a `.subckt` body is caught under its final
  node name too. Node comparison is ASCII-case-insensitive because the grammar itself treats `A`
  and `a` as one node (verified directly: `V1 A 0 5` + `R1 a 0 1k` yields a single `V(A)`).
- Deliberately `Sig2Phys`-only, not "any block name colliding with any node name": wiring any
  other block kind is the same silent-zero shape, but a blanket rule would also reject the
  harmless and plausible habit of naming a `kind=phys2sig` probe after the node it measures.
  `Sig2Phys` is the only kind that claims to drive the physical domain, so it is the only one
  anybody is tempted to draw a wire from.
- `crates/general-simulator-cli/src/main.rs`: calls the same check once, before the
  `dc`/`transient` branch. This is what makes `--mode dc` fail too — that path never enters the
  block-graph engine at all (`solve_dc` takes no blocks), so the library-level check alone would
  have left DC silently returning `0`. The CLI also renders this one variant with a spelled-out
  message instead of the bare `{e:?}` dump every other `DaeError` gets, keeping the `{e:?}`
  prefix so the variant name stays greppable: the whole failure mode was that the wrong answer
  was indistinguishable from a legitimately-zero node, so the error has to say what to write
  instead.

**Verification.**
- `crates/dae-runtime/tests/sig2phys.rs`: three new tests — the exact silent-zero construction
  is now `Sig2PhysUsedAsCircuitNode` before any step runs; the same mistake written in the other
  case (`R1 a cmd_v` against `CMD_V`) is rejected identically and names the first offending
  element and the node token as written; and a node merely sharing a *non*-converter block's
  name still solves normally.
- The legitimate paths are unaffected and still covered:
  `sig2phys_gate_enforcement.rs::wrapping_the_same_block_in_a_domain_voltage_sig2phys_makes_it_work`
  (switch `gate=`/`ctrl=`) and `sig2phys.rs`'s exact-value source-driving tests.
- `doc-verify/sig2phys/error_converter_wired_as_a_node.cir` + two new CLI-level tests covering
  `--mode transient` and `--mode dc`, asserting the guidance text and that nothing is printed
  before the rejection.
- Gates: `cargo fmt --all --check` clean, `cargo clippy --all-targets -- -D warnings` clean,
  `cargo test --workspace` 244 passed / 0 failed, `cargo test -p dae-runtime --features python`
  green, full `doc-verify` suite green (every component folder, with the CLI built
  `--features python`). `general-mna`'s own suite re-run unchanged and green (68 tests).

**What remains.**
- `general-mna`'s `BlockKind::Sig2Phys` doc comment still owes an `## Errors` bullet for this
  case (the Component Reference is generated from it). Not done here: this session could not
  perform git operations against the sibling `general-mna` checkout, and the fix needed no code
  change there.
- `gsim-core` should refuse to *construct* the illegal document: a `converter.sig2phys` block's
  physical-side port must only ever be referenced by name from a `gate=`/`ctrl=`-style field or
  a source's value field, never connected by an ordinary `Wire`. Its compiler emits the block
  name as a node token today, which is exactly what this check now rejects downstream.
- Nothing further is owed on the "controlled source" question: `E`/`G`/`F`/`H` are already
  implemented, and the signal-driven case is the `V1 a 0 <converter>` form above.

## 2026-09-11 07:45 — `--out-every N`: decimate output without coarsening the timestep

Closes #5.

**Why.** Verifying zero-voltage switching needs a step below the *hard* discharge time of the
switching node, `r_on * C_oss` — 0.4 ps at 1 mΩ and 400 pF. A larger step steps clean over the
discharge and soft and hard switching become indistinguishable, so every leg reports perfect
ZVS: a silent, uniform, entirely convincing failure. A 150 ns commutation window at `--dt 4e-14`
is 3.75 M points, about 2.5 GB of CSV at ~55 columns, for a measurement that needs a few
thousand. The run was affordable to compute and not to write down, and nothing separated the
integration step from the emit rate.

**What.** `--out-every N` writes every Nth resolved point, default 1.

- Serialization only. Every step is still taken; the solution is bit-identical.
- `kind=measure` still sees every point. Decimating a measurement's input would change its
  *answer* rather than its size — a different feature, and a worse one. This is why the
  in-memory path decimates a copy (`decimate()`) and passes the undecimated `waveform` to
  `write_measurements_log`.
- `--out-every 0` is rejected with a message rather than dividing by zero or emitting nothing.

**Two output paths, two implementations.** The in-memory path decimates a finished `Waveform`;
the streaming path (`run_transient_streamed`, taken by any netlist with a block or an ideal
switch — i.e. every switched-converter deck) gates the write inside the solver callback on a
resolved-point counter. Both are tested, because they are genuinely separate code.

**Tests** (`crates/general-simulator-cli/tests/out_every_cli.rs`, 4): kept rows are byte-for-byte
the full run's rows at those indices — on *both* paths; `--out-every 1` is byte-identical to the
default; `0` is rejected. Asserting "the file got smaller" would pass for an implementation that
coarsened the timestep instead, which is exactly the mistake the flag exists to avoid, so the
test asserts row identity instead. New fixture `rc_with_block.cir` exists only to reach the
streaming path.

**Docs.** `book/user-guide/src/cli-reference.md` gains the flag, the "why" with the ZVS numbers,
and an explicit note that this is *not* a substitute for adaptive stepping — an adaptive
controller would lengthen the step across exactly the flat dead band where the discharge is
about to happen.

**Gates.** `cargo fmt --all -- --check` clean, `cargo clippy --all-targets -- -D warnings` clean,
`cargo test --workspace -- --test-threads=1` 253 passed / 0 failed.

**Noticed in passing, filed as #6, not fixed here.** `cargo test --workspace` at the default
parallelism fails intermittently in `cscript-ffi` with a *different* subset of tests each run —
present on `da07143` with no local modifications, and passing single-threaded. The fixtures
appear to race on compiling/`dlopen`ing the same shared object. It matters because
`cargo test --workspace` is a required gate in `AGENTS.md`, and an intermittent failure trains a
reader to ignore it.

## 2026-09-14 11:31 — `kind=clamp` turned out to already exist, as `kind=limit`

Requested: a `kind=clamp` block taking three *signal*-valued inputs (`x`, `lo`, `hi`) and
computing `min(max(x, lo), hi)`, motivated by an internal three-phase PFC experiment whose
anti-windup clamp only bounded the PID block's own output, not the final command sent to the
bridge — the fix needs to clamp that final command to a time-varying bound (`±Vdc/2`), which the
existing `kind=saturation` (`BlockKind::Saturation(f64)`, a fixed netlist constant) cannot do.

Read `general-mna/src/block_graph.rs` and `system_builder.rs` end to end for the multi-signal
stateless-block pattern before writing anything, per plan — and found `BlockKind::MathFn3`
(`continuous_blocks::waveform_arithmetic::MathFn3::Limit`, netlist keyword `kind=limit`)
already does exactly this: `limit(x, y, z) = x.clamp(min(y,z), max(y,z))`, with `in1=`/`in2=`/
`in3=` all ordinary `Signal` inputs — no different from wiring a block's output into `x=`/`lo=`/
`hi=` would have been. It is already documented (component reference, "Waveform Arithmetic
Functions (ternary: if, limit)"), already has a committed `doc-verify` example
(`doc-verify/mathfn/example_fn3.cir`, `test_example_fn3_if_select_and_limit_clamp`), and already
had two of the three hand-derived cases this task called for.

Per `AGENTS.md`'s "Do not duplicate work the sibling repos already do correctly" and this
project's own no-duplication stance applied within a single repo: implementing a second,
parallel `BlockKind::Clamp` with identical semantics under a different name would be pure
duplication for a cosmetic naming preference, not a real capability gap. So Part 1 of this task
became: confirm `kind=limit` truly covers the need (it does — order-independent bounds, signal
inputs, already wired end to end), and close the one real gap found — the hand-derived test set
was missing the below-`lo` case. Added it:

```rust
assert_eq!(limit(5.0, 0.0, 3.0), 3.0);  // clamp(5, 0, 3) == 3 (above hi)
assert_eq!(limit(-2.0, 0.0, 3.0), 0.0); // clamp(-2, 0, 3) == 0 (below lo)
assert_eq!(limit(1.0, 0.0, 3.0), 1.0);  // clamp(1, 0, 3) == 1 (inside range)
```

## 2026-09-22 13:29 — cscript fixture compile race: compile once per process, never overwrite in place

Closes #6, resolves GOTCHA-001.

**Diagnosis, confirmed rather than assumed.** On `d5a8fa3`, 8 consecutive
`cargo test -p cscript-ffi` runs at default parallelism: run 8 failed
`two_instances_of_the_same_library_keep_independent_state`,
`stateful_fixture_accumulates_across_calls` and
`update_is_a_silent_no_op_when_the_library_does_not_export_it` — all users of
`libaccumulator.so`. `compile_fixture` compiled the fixture on *every* call straight to
`$TMPDIR/cscript-ffi-test-fixtures/lib<name>.so`; `cc -o` truncates that path in place, so a
sibling test thread's `dlopen` of the same path could land on a half-written file. The three
CLI test binaries (`cscript.rs`, `sample_time_cli.rs`, `cscript_update_cli.rs`) each carried a
copy of the same helper aimed at `general-simulator-cli-test-fixtures/`, with the extra twist
that the `dlopen` there happens in a spawned `general-simulator` child. And the directory is
shared across processes: while this was being fixed, another agent's worktree of this repo was
writing `libaccumulator_checkpoint.so` into the very same directory.

**Change.** One contract, implemented in `crates/cscript-ffi/tests/fixtures.rs`
(`compile_source`/`compile_fixture`) and in a new shared
`crates/general-simulator-cli/tests/support/mod.rs` (`compile_c_fixture`, replacing the three
per-file copies):

- a `static OnceLock<Mutex<HashMap<String, PathBuf>>>` registry — each fixture is compiled at
  most once per test process, and the mutex is held across `cc`, so two threads never compile
  the same fixture twice;
- the `.so` lives in `<temp>/<crate>-test-fixtures/<hash(source + cc flags)>/lib<name>.so`, so
  an edited fixture never reuses a stale library and an identical one from an earlier process
  is safely reused;
- `cc` writes to `lib<name>.so.<pid>.tmp` and the result is `rename`d into place — atomic, and
  an already-`dlopen`ed inode stays valid for whoever mapped it.

The synthesized `broken_missing_output` fixture goes through the same `compile_source` path
instead of its own inline `cc`. No test's assertions changed.

## 2026-09-22 13:32 — `pspwm`'s `phase` input is a lead, documented and proven

Closes #3.

**Truth from code.** `crates/dae-runtime/src/block_graph.rs`'s `PhaseShiftPwm` arm gates on
`theta = (*phase + phase_offset).rem_euclid(1.0)` — the `phase` input is *added* to the
integrated carrier, so a positive command advances every edge. A block commanded phase $p$
begins its on-interval at $t_{\text{on}} = (1 - p)\,T$, not $p\,T$. The existing wording pinned
the units (cycles, distinct from the integrator state) but not the direction, and for a single
modulator the sign is invisible — it only bites once two legs must hold a relationship.

**Confirmed with the release CLI** (`cargo build --release -p general-simulator-cli
--features python`): two `pspwm` blocks at 1 Hz, 50 % duty, one `phase=0` (`REF`), one
`phase=0.25` (`LEAD`), `--dt 0.125`. `LEAD` rises at $t = 0.75$ s, `REF` at $t = 1.0$ s — a
quarter period earlier; `LEAD` also falls at $0.25$ s against `REF`'s $0.5$ s. First tried
`--dt 0.1`: the accumulated `0.1` rounding puts `REF`'s wrap at $t = 1.1$ s instead of $1.0$ s,
which is a floating-point artifact of the phase integrator, not the lead — so the fixture uses
the exactly-representable $\Delta t = 0.125$ s (8 steps per period) where every wrap lands on
the grid.

**Change.**
- `book/user-guide/src/gate-bindings.md`: new subsection "`pspwm`'s `phase` input is a lead,
  not a lag" — the gating formula in LaTeX, the $t_{\text{on}} = (1 - p)\,T$ rule, the
  two-block run with its observed edge times, why the sign hides in a single modulator and can
  partially cancel in a symmetric bridge, and the `phase` $= 1 - s$ recipe for a lag.
- `book/user-guide/src/block-library.md`: the `pspwm` row says `phase` is a lead and points
  at the chapter.
- `doc-verify/pspwm/phase_lead.cir` + `test_pspwm.py::test_phase_input_is_a_lead_not_a_lag`
  (asserts the full 8-sample pattern of both outputs, the rising-edge times $0.75$ and $1.0$,
  and their difference $0.25$) + README line. `doc-verify/pspwm`: 6/6.

**Owed in `general-mna`** (read-only here): the `BlockKind::PhaseShiftPwm` `## Parameters`
bullet for `phase` should gain "Applied as a **lead**: conduction begins at `(1 - phase)` of
the carrier period, so a phase of `0.25` starts the pulse three quarters of the way through
the period, not one quarter." — the Component Reference is generated from that comment.
