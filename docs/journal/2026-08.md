## 2026-08-17 10:09 — Milestone 3 (`dae-runtime`, generic circuit + diode fold) complete

Resolved the Milestone-2 open question: extended the sibling `elspice-mna` repo's public API
(commit `9d190db` there) to stamp `'D'` elements as a fixed symbolic conductance
(`{name}_G`) plus a Norton current source (`{name}_Ioff`) — reusing its existing
`stamp_admittance`/`stamp_current_source` functions verbatim, no new MNA unknowns — and
extended `NumericMnaSystem::evaluate()` to also numerically resolve the RHS (`input_values`,
`u`), which it previously left symbolic. Caught and fixed a real regression along the way: an
initial version made RHS evaluation mandatory, which broke an existing `elspice-mna` test that
legitimately leaves one source symbolic; fixed by making unresolved inputs contribute `0.0`
rather than erroring (see that repo's own journal for the full account).

Then built `crates/dae-runtime` here: given a netlist (parsed via the new `'D'` stamp) plus a
`BTreeMap<String, pwl_devices::Diode>` of PWL parameters, it fixes every diode's `elspice-mna`
conductance at its own canonical reference slope (`g_off`) — making the resulting linear
system genuinely fixed, independent of which segment every diode is in — solves it once for a
baseline `x0`, and once more per diode for a sensitivity vector `w_j` (`A0 * w_j =` that
diode's `B` column). Every diode's terminal voltage is then an affine function of every
diode's canonical `z` variables (including real cross-coupling between diodes sharing nodes,
via `w_j` evaluated at another diode's terminals — not just a self term), which folds directly
into the LCP `(M, q)` `lcp-solver` already solves. Full derivation and the generalization from
Milestone 2's single-topology hand fold: `docs/architecture.md` and `src/lib.rs`'s module
doc comment.

Verification: `tests/two_diode_via_netlist.rs` rebuilds Milestone 2's exact two-diode circuit,
but from real netlist text through the generic fold instead of a hand-typed `(M, q)` — and
reproduces the same already-hand-verified numbers (`e2 = 7/3`, `V = 8/3`,
`I_D1 = 5/3`, `I_D2 = 2/3`, then the lower-source-voltage only-one-diode-conducting case) on
the first run. Reproducing known-correct numbers via a structurally different, general-purpose
code path is real evidence the fold is correct, not just that it compiles. `dense_solve`
(hand-rolled Gauss-Jordan, deliberately not `faer` yet — see its own module doc for why) has
its own two unit tests. `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets
-- -D warnings`, `cargo test --workspace` all clean (15 tests total).

Scope note: this is a **DC operating point** solve only (`K`/storage ignored, `dx/dt = 0`) —
transient integration (the trapezoidal/backward-Euler timestep loop) is Milestone 6, not yet
built. The MOSFET model, `continuous-blocks`, and `elspice-pwl-cli` are Milestones 4-5,
also not yet built.

## 2026-08-17 09:53 — Milestone 2 (`pwl-devices` diode + first circuit fixture) complete

Implemented `crates/pwl-devices`: a 3-segment PWL diode (`src/diode.rs`) via the Chua-Lin
canonical decomposition into `max(0, ...)` terms — exactly the `z` variables an LCP resolves
(see `docs/architecture.md`, "Mode selection as a Linear Complementarity Problem"). Verified
the decomposition against an independently written direct piecewise formula (unit tests:
agreement across all three segments and exactly at both breakpoints, continuity at both
breakpoints, rejection of `v_breakdown >= v_th`).

Then `tests/two_diode_circuit.rs`: hand-built the PCNR paper's illustrative two-diode-plus-
resistor circuit (substituting PWL diodes for its exponential ones) as an LCP by folding each
diode's canonical form through the single-node KCL equation, solved via `lcp-solver`, and
checked the result against two operating points worked out by hand *before* the code was
written (both diodes forward-conducting; then only one, with the source lowered below the
second diode's threshold). Both match to `1e-6`. This is the first proof this project's
approach actually works end to end on a real (if small) circuit, with no Newton-Raphson
anywhere.

`cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets -- -D warnings`,
`cargo test --workspace` all clean.

Next (Milestone 3, per `docs/architecture.md`/the approved plan): wire this into `elspice-mna`
for full linear-circuit-plus-diode netlists. This needs a decision — extend `elspice-mna`'s
public API with a minimal, additive extension point for externally-stamped devices, or have
`dae-runtime` do its own minimal linear-device stamping directly from `spice-core`'s AST — the
plan explicitly deferred this until `pwl-devices`' data shapes existed. They now do
(`Diode`/`DiodeCanonical`). Flagged for the user before touching the `elspice-mna` repo, since
any change there is a cross-repo decision outside this repo's own boundary
(see `AGENTS.md`, "Project boundaries").

## 2026-08-17 09:46 — Repo scaffolded, Milestone 1 (`lcp-solver`) complete

Created this repo as a new sibling to `spice-lsp` and `elspice-mna`, per the approved plan
(a Newton-free, LCP-mode-selected PWL circuit + continuous-block simulator — full rationale
in `docs/architecture.md`, derived from the voltage-limiting discussion already recorded in
`internal-archive`'s `explanations/xyce/`).

Implemented `crates/lcp-solver`: Lemke's algorithm over a dense simplex-style tableau
(`src/tableau.rs`, `src/lemke.rs`), all-ones covering vector by default with a
`solve_with_covering_vector` escape hatch for a general positive `d` (fixed a real bug during
review: the initial pivot row must minimize `q_i / d_i`, not raw `q_i`, for a general covering
vector — they only coincide when `d` is all-ones).

Verification: six tests in `crates/lcp-solver/tests/fixtures.rs`, each with an independently
hand-derived expected solution (not just internal self-consistency) — trivial no-pivot case,
single-pivot scalar case, a positive-definite case needing multiple pivots, a degenerate
boundary case (two variables simultaneously zero), a general "solution satisfies its own
definition" sweep across all fixtures, and a genuinely infeasible LCP that correctly returns
`LcpError::RayTermination` instead of fabricating an answer. `cargo fmt --all -- --check`,
`cargo clippy --all-targets -- -D warnings`, `cargo test --workspace` all clean.

No circuit-facing code exists yet by design — `lcp-solver` is meant to be trusted standalone
before `pwl-devices` (Milestone 2) touches it. Next: the PCNR two-diode circuit as the first
real PWL-diode fixture (see `docs/architecture.md`, "Status").
