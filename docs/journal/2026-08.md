## 2026-08-27 14:57 — Python function blocks (`kind=pyblock`): design doc + full implementation

Requested as a a reference tool-Function-block-style escape hatch to Python (`numpy`/`scipy` usable
directly), with the design written up and measured before any code, mirroring
`vector-signals.md`'s own before/after pattern — `book/dev-guide/src/python-blocks.md`.

**Verified the environment before designing around it, rather than assuming**: confirmed PyO3
0.29.2's `auto-initialize` feature embeds the system's own Python 3.14.4 cleanly (a standalone
probe crate, `Python::attach` + a trivial call, before committing to the design), and measured
real per-call overhead with a committed benchmark (`crates/pyblock-ffi/examples/bench.rs`,
`cargo run --release --example bench`) instead of guessing: bare `Python::attach` ~95ns, a
scalar function call ~150-300ns, a numpy-array round trip ~0.9-1.4us — all far cheaper than the
"microseconds to tens of microseconds" estimate given before measuring, and the same order of
magnitude as `cscript`'s own C FFI call.

New crate `crates/pyblock-ffi` — the Python-hosted counterpart to `cscript-ffi`, deliberately a
*different* PyO3 integration from `general-mna`'s own existing `python` feature (that compiles
`general-mna` itself *into* a Python extension module, `extension-module`, now deprecated
upstream; this embeds Python *into* the Rust binary, `auto-initialize` — the two can't share a
crate). Contract mirrors `cscript_ffi` closely: `start()`/`output()` (or `derivative()`/
`output_xc()` instead, under the same `xc_count` split `CScript` already has), same
`sample_time` zero-order-hold convention. Two genuine improvements over the C path, both
recorded in the design doc: cloning uses Python's own generic `copy.deepcopy` (no author
opt-in needed, unlike `cscript_clone`, so there's no "doesn't support adaptive stepping"
rejection path for `PyBlock` at all), and a Python exception is a catchable, clearly-named
`PyBlockError` rather than undefined behavior. Inputs also don't need `cscript`'s own
flattening: Python can keep each declared `inputs=` signal's own scalar/vector shape as a
`float`/`numpy.ndarray` list entry, instead of concatenating everything into one flat array.

`dae-runtime`'s own `BlockState::PyBlock` and `evaluate_blocks` arm mirror `CScript`'s almost
line for line (same due/sample_time gating, same step-xc-then-compute-output ordering); new
`DaeError::PyBlock(pyblock_ffi::PyBlockError)`. `general-simulator-cli`'s CSV-column listing
extended the same way every other multi-output kind already was.

Two real findings while building it (both in the design doc's own "Two real findings" section,
not glossed over): `derivative()`'s return value needed its own extraction path, not
`output()`'s shared one — a length-1 continuous state is still conceptually a vector (`derivative`'s
own docstring says "array-like, same length as `xc`," unconditionally), so it can't get the
same bare-scalar shortcut a single scalar *output* gets; caught by a failing xc test
(`TypeError: must be real number, not list`) on the very first `xc_count=1` fixture tried. And
`path=`/`lib=` fields can't contain whitespace anywhere in the value (no quoting support in the
netlist grammar) — not new to this session, but surfaced directly since the test fixtures
happened to live under a path containing a space; both `pyblock`/`cscript` CLI tests now copy
fixtures into `std::env::temp_dir()` before referencing them from netlist text.

Verified end to end at every layer: `pyblock-ffi`'s own 9 fixture tests (stateless/stateful/
independent-instance-state/deepcopy-clone/vector-input/xc-closed-form/contract-mismatch-errors/
Python-exception-propagation/missing-function-errors), `dae-runtime`'s 3 integration tests (a PI
controller matched against a hand-computed recursion, vector-shape preservation through the real
block graph, an `xc` closed-form step response), and a `general-simulator-cli` end-to-end test
through the real compiled binary and a real `.py` file on disk. Every existing test in the
workspace (46 test binaries) passed unchanged. `cargo fmt`/`clippy --workspace --all-targets -D
warnings`/`test --workspace --release` all clean.

## 2026-08-27 12:44 — Vector-signal support implemented (per `vector-signals.md`), StateSpace now genuinely MIMO

Implements the design survey (`book/dev-guide/src/vector-signals.md`), with its three flagged
open questions answered: `Gain`/`Const` extend their existing kind's own payload rather than
gaining a sibling `BlockKind` (both come from `general-mna`, which owns the type now — see that
repo's own journal entry, same session); `CoordinateTransform`/`Pmsm`/`cscript` keep scalar-only
outputs (no additive whole-vector alias); a `Vector`-valued CSV column expands to `NAME[0]`,
`NAME[1]`, ... derived from the first trace row's own resolved shape (arity is fixed for the
whole run once declared, so this is exactly as valid as a separate static pass, and reuses this
function's own existing "build the header from the first row" convention).

`evaluate_blocks`' entire dispatch match was rewritten around `SignalValue` instead of `f64`, one
rule per category from the survey: `MathFn1`/`Table` map elementwise over a `Vector`, never
reject; `MathFn2`/`MathFn3` broadcast a lone `Scalar` operand against a `Vector` (mismatched
`Vector` lengths reject); `Sum`/`Product` require all-`Scalar` or all-`Vector`-same-length,
*rejecting* a mix rather than broadcasting (no unambiguous placement for a lone scalar once more
than one vector's already present — the one place this diverges from `MathFn2`'s rule);
`Gain`/`Saturation` broadcast their own scalar parameter across a `Vector` input, `Gain`'s matrix
mode requires an exactly-sized `Vector` and produces one; `Pid`/`Vco`/`Hysteresis`/
`TransferFunction`/`Pwm`/`PhaseShiftPwm`/`Sig2Gate`/`Sig2Voltage`/`Sig2Current` all reject a
`Vector` input outright via a new shared `require_all_scalar` helper (the default, fail-closed
rule for anything without its own broadcast/elementwise story); `StateSpace`/`CoordinateTransform`/
`Pmsm`/`cscript` flatten their own declared inputs (scalar or vector, concatenated in order) via
a new shared `flatten` helper — the input-bundling convention that directly answers the
motivating "let a `cscript` block consume a whole upstream vector as one wire" question, with
**zero `cscript_ffi`/C ABI change** (the flat `in[]`/`in_len` array was already exactly this
shape; only how Rust assembles it changed).

**`StateSpace` is now genuinely MIMO** — the actual "turn SISO into MIMO" request:
`continuous_blocks::StateSpace` already supported a general `(A,B,C,D)` system (confirmed by
reading it directly, not assumed); only this crate's own `evaluate_blocks` arm hardcoded a
single input/output (`let u = [input_vals[0]]`, always `output[0]`). Split the old combined
`StateSpace | TransferFunction` match arm in two: `TransferFunction` stays strictly SISO
(rejects a `Vector` — a rational `N(s)/D(s)` has no matrix generalization the way `(A,B,C,D)`
does), `StateSpace` now flattens its inputs to the exact length `state_space.inputs()` requires
(a clear `DaeError::VectorSignalSizeMismatch` otherwise) and returns `Scalar` when
`outputs()==1` (byte-identical to every existing SISO declaration) or `Vector` when `>1`.

Two new `DaeError` variants: `VectorSignalNotSupported`/`VectorSignalSizeMismatch`, both naming
the offending block. `TransientWithBlocksStep`'s own output map is now `SignalValue`-valued;
`fold_and_solve`'s `extra_values`/`extra_values_prev` (the `V`/`I` source `Sig2Voltage`/
`Sig2Current` substitution path) deliberately untouched — a new `scalar_only` helper filters the
`SignalValue` map down to its `Scalar` entries right before those calls instead, since the only
symbols that can legitimately appear there are already guaranteed `Scalar` by `Sig2Voltage`/
`Sig2Current`'s own rejection rule.

**Every existing test in the workspace passed unchanged** after the rewrite (only a mechanical
`.as_scalar().unwrap()` needed at direct-`outputs["name"]`-indexing call sites in hand-written
Rust tests, since the return type changed) — confirms the whole rewrite is exactly behavior-
preserving for every previously-scalar-only case. New `crates/dae-runtime/tests/vector_signals.rs`
(8 tests: MIMO `StateSpace` two ways — several scalar signals and one bundled vector signal, both
checked against an exact closed-form since `x'=const` has zero RK4 truncation error; the size-
mismatch rejection; `MathFn1` elementwise; matrix `Gain` both the correct case and the scalar-
input rejection; `Sum`'s vector-accept/mixed-reject rule; `Pid`'s vector rejection) plus a new
CLI-level end-to-end test in `python_list_syntax_cli.rs` (`b=`/`c=`/`d=` matrices and `inputs=`
through the real netlist parser, checking the `Y[0]`/`Y[1]` CSV column expansion). `cargo fmt`/
`clippy --workspace --all-targets -D warnings`/`test --workspace --release` all clean.

## 2026-08-27 12:00 — `cscript`'s optional continuous-state (`xc`) contract

Followed a design discussion about `cscript`'s state model — the existing single-function
contract (`cscript_output`, mutating an opaque `void *state` blob) covers a block that manages
its own state entirely by hand, but has no way to give the *solver itself* a state to
numerically integrate. Added exactly that as a strictly additive, opt-in extension.

`cscript_ffi` (`crates/cscript-ffi/src/lib.rs`): two new optional C exports, used *instead of*
`cscript_output` (never alongside it) —

```c
void cscript_derivative(void *state, const double *in, int in_len,
                         const double *xc, int xc_len, double *xc_dot, int xc_dot_len);
void cscript_output_xc(void *state, const double *in, int in_len, double dt,
                        const double *xc, int xc_len, double *out, int out_len);
```

`xc` itself lives in `dae-runtime`'s own `BlockState`, not inside the opaque blob — the one
place this contract breaks "everything opaque to Rust," deliberately: the solver's own RK4
stepper needs plain vector arithmetic on it between stages. `CScriptInstance` gained
`derivative`/`call_xc`/`rk4_step_xc` (the last holding `in` fixed across all four RK4 stages —
the same zero-order-hold convention `continuous_blocks::StateSpace::rk4_step` already uses for
every other dynamic block, so a `cscript` block's own continuous state integrates by the same
rule, not a separate one). `CScriptRegistry` gained `instantiate_xc` alongside the existing
`instantiate`, each validating its own required-symbol combination up front (mirroring the
existing `cscript_clone`-required-for-adaptive-step check) rather than deferring to a runtime
panic; `instantiate`'s own existing behavior (and every prior test exercising it) is completely
unchanged, since `output` moved from a required to an optional field validated lazily instead of
at load time.

`general-mna`'s `BlockKind::CScript` gained `xc_count: usize` (default `0`) and `xc_count=<n>`
netlist parsing (that repo's own commit/journal has the type/parsing half of this change, split
per the ongoing format-unification plan). `dae-runtime`'s `BlockState::CScript` gained an `xc:
Vec<f64>` field (starts at rest, like every other dynamic block); its `evaluate_blocks` arm
steps `xc` via RK4 first, then computes output from the *new* `xc` — the same ordering
`StateSpace`/`TransferFunction`'s own arm already uses (step state, then read output from the
updated state), applied under the same `sample_time` zero-order-hold gating the rest of the
block already had (a block wanting continuous, every-circuit-step integration simply leaves
`sample_time` unset, exactly as it already would for the discrete half).

Verified two ways: `cscript-ffi`'s own new fixture (`decay_xc.c`, `dx/dt = -K*x + u`) checked
against the closed-form solution to `1e-9` via `rk4_step_xc` directly, and a full CLI-level
end-to-end test (netlist `xc_count=1` -> real compiled `.so` -> `general-simulator` binary)
checked against the closed-form step response to `1e-6`. Every existing test (both new-repo
`cscript` fixtures, and — checked separately in the sibling `internal-archive` repo —
every existing `cscript`-based controller experiment, all declaring `xc_count=0` implicitly by
omission) needed zero changes. `cargo fmt`/`clippy --all-targets -D warnings`/
`test --workspace --release` all clean across `cscript-ffi`, `dae-runtime`, and
`general-simulator-cli`.

## 2026-08-24 14:32 — Phase 3: `dae-runtime` stops re-parsing raw netlist text, hierarchy support

`general-mna` (Phase 3, own journal entry) gained `.subckt`/`X`-instance flattening
(`hierarchy::flatten`), but testing it end-to-end through this crate's real CLI binary
immediately failed: `dae-runtime`'s own solve loop never used `general_mna::build_system`'s
already-flattened output at all — it independently re-parsed the *raw* netlist text itself, at
~10 separate call sites (`solve_dc`, `simulate_transient`, `build_with_mosfets`, a separate
`topology::diode_nodes(source, dialect)` call re-parsing purely for diode terminal names, and
per-timestep re-evaluation of transient sources), all calling `MnaBuilder::build_fragment(source)`
directly on unflattened text. An `X`/`.subckt` line reached the real solver completely unflattened
and errored out as an unsupported element.

Asked the user how to fix this (text-round-trip serialization vs. a real refactor to thread
pre-parsed statements through); chose the refactor. Changes:

- `topology::diode_nodes` now takes `statements: &[Statement]` (already parsed) instead of
  `source: &str, dialect` — no more re-parsing per diode-topology lookup.
- Every public entry point (`solve_dc`, `simulate_transient`, `solve_dc_with_mosfets`,
  `simulate_transient_with_mosfets`, `block_graph::simulate_transient_with_blocks`,
  `closed_loop::simulate_closed_loop`) keeps its existing `source: &str, dialect: Dialect`
  signature (so none of the ~17 existing test files or the CLI needed call-site changes) but now
  calls `general_mna::parse_and_flatten` exactly once at entry, then threads the resulting
  `Vec<Statement>` through every private helper (`fold_and_solve`, `step_with_fallback`,
  `build_with_mosfets`, `step_control::{lte_attempt, adaptive_step}`) instead of raw text. This
  also removes a real, previously-unnoticed perf issue: `fold_and_solve` (called once per LCP
  fold, i.e. every single solved trial at every timestep) used to re-parse the entire netlist
  from scratch on every call via `topology::diode_nodes(source, dialect)`; now it's parsed once
  per run (or once per timestep for the MOSFET/gate-rebuild paths, which already had to rebuild
  the symbolic `MnaSystem` every step regardless — but no longer re-*parse* text to do it).
  `dialect` dropped entirely from `fold_and_solve`/`step_with_fallback`/`lte_attempt`/
  `adaptive_step` (no longer needed once the statements are already parsed).
- New `DaeError::Parse(String)` variant for a hierarchy/parse failure, distinct from
  `DaeError::Build`'s "parsed fine, but this statement has no valid stamp" class.

Verified end-to-end with a hand-written two-instance RC-subckt netlist run through the real CLI
binary (`--mode transient`) — this is also where a real ground-scoping bug in `general-mna`'s
`hierarchy::flatten` was caught (see that repo's own journal entry) and fixed; after the fix, the
CSV output shows correct ~1ms (`R*C`) charge/discharge behavior per stage, confirming the whole
pipeline (parse → flatten → `MnaBuilder`/block-graph build → LCP-fold solve loop) now genuinely
resolves `.subckt` hierarchy rather than merely accepting the syntax.

`cargo build --release --workspace`, `cargo test --workspace` (0 failures across every existing
test file — the whole point of keeping public signatures unchanged), and `cargo clippy
--workspace --all-targets -- -D warnings` all clean.

## 2026-08-23 22:55 — PWM modulator architecture redesign: two fused, block-driven, dead-time-capable modulators

User asked for a survey of existing PWM/gate mechanisms, then a full redesign, driven by a
concrete DAB H-bridge modulation need (a TIDA-010954-style primary bridge: two legs sharing one
controller-driven switching frequency, one leg's phase fixed at 0, the other's phase driven by
the controller's own inner-angle output, both legs at ~0.5 duty). Explicit requirements, in
order:

1. **PWM Modulator 1** (duty-driven, fixed frequency) must generate its own active-high
   complementary pair, fusing the old `GateBinding::Pwm`/`PwmComplement` into one component.
2. **`GateBinding::Fixed`/`PwmFixed` removed** — "not block driven... we don't want many
   blocks." Even a permanently-on/off gate is now an ordinary `Const` block wrapped in
   `sig2gate`, no special escape hatch.
3. **`GateBinding::Block` kept** — confirmed as the right call: it becomes the *only* remaining
   `GateBinding` variant, the universal "read a named block's current output, threshold at 0.5"
   consumer for anything gate-driving (a PWM modulator's own output, a `Hysteresis` block, a
   hand-built comparator chain) — exactly the user's own guess about what it was for.
4. **PWM Modulator 2** (`Vco`/`VcoPhase` fused, `duty` newly block-driven alongside `freq`/
   `phase`) — explicitly told **not** to call it "vco" anywhere, even internally, since it's a
   different thing (own frequency-integration state, not a shared oscillator block a `Vco`
   reader points at) — reusing the identifier would misleadingly imply an inheritance
   relationship that doesn't exist. Gets its own `BlockState::PhaseShiftPwm` variant (distinct
   from `BlockState::Vco`, even though both compose the same `continuous_blocks::Vco`
   clamp-and-integrate math internally) and its struct field is `osc`, not `vco`.
5. **Dead time**, active-high-complementary style, confirmed against the user's own precise
   edge-delay description before implementing: only the two *rising* (turn-on) edges are ever
   delayed (`red` delays the main signal's own turn-on, `fed` delays the complement's own
   turn-on) — falling edges are never delayed, which is what actually guarantees both outputs
   are provably off during the gap. `red=fed=0.0` (the default) recovers the ideal pair exactly.
   One shared implementation (`continuous_blocks::math_ops::complementary_pwm_with_deadtime`)
   used by both modulators, so "how dead time is inserted" has exactly one answer — "the same
   rule for any block generating control signal for the gate of switches," per explicit
   instruction.

Implementation: `BlockKind::Pwm { freq_hz, red, fed, output_names }` (Modulator 1, stateless —
a pure function of `(t, duty)`, no internal oscillator) and `BlockKind::PhaseShiftPwm { osc,
red, fed, output_names }` (Modulator 2, owns its own frequency-integration state — two
instances fed the *same* `freq` input stay bit-for-bit phase-synchronized, deterministic
integration/same `dt`/same starting phase, without a separately-declared shared oscillator
block in between, unlike the old `Vco`-sharing design). Both are two-output blocks (`main`,
`complement`) following the existing `CScript`/`CoordinateTransform`/`Pmsm` `output_names`
convention. `GateBinding` collapsed to a single `Block(String)` variant (kept as a named
one-variant enum, not erased entirely, per explicit preference for future extensibility).
`elspice-pwl-cli`: `kind=pwm freq=<hz> in=<duty> [red=] [fed=] [outputs=]` and `kind=pspwm
f_min=<hz> f_max=<hz> inputs=<freq>,<phase>,<duty> [red=] [fed=] [outputs=]`; `gate=` grammar
reduced to exactly `gate=block ctrl=<sig2gate-name>`, every other spelling (`on`/`off`/`pwm`/
`vco`/`dutyctrl`/`dutyctrlcomplement`/`vcophase`) removed, `--mode dc` now unconditionally
rejects any netlist with a MOSFET (no gate spelling left that a DC operating point could
resolve). Full module doc comment in `main.rs` rewritten (grammar reference, worked example)
to match.

Caught two real bugs verifying by hand rather than trusting the design on paper: (1) a
CLI-level smoke test's `outputs=MOD1_MAIN,MOD1_COMP` explicit override didn't make `MOD1_MAIN`
resolvable — the *primary* output is always bound under the block's own declared name (`MOD1`),
never `output_names[0]` (that slot is purely a self-documentation label matching the existing
`CScript`/`CoordinateTransform`/`Pmsm` convention, not itself a lookup key) — caught the same
mistake in two hand-written Rust-API tests too, all fixed to reference the block's own name for
the primary output. (2) `run_transient_with_mosfets`'s own extra-output-name CSV-column list
(needed so a multi-output block's *secondary* names show up as their own columns) hadn't been
extended for the two new block kinds — `MOD1_COMP` silently never appeared in a smoke test's
own CSV header despite resolving fine internally; fixed by adding `Pwm`/`PhaseShiftPwm` to that
match alongside `CScript`/`CoordinateTransform`/`Pmsm`.

Verification: `math_ops::complementary_pwm_with_deadtime` (3 new unit tests: zero-dead-time
exact partition, nonzero-dead-time gap boundaries against hand-computed edges, a 1000-point
sweep confirming never-both-on regardless of dead time); `pwm_complement_gate.rs` (rewritten,
2 tests: zero-dead-time mutual exclusivity + nonzero-dead-time gap enforcement, both against a
real two-MOSFET circuit); `phase_shift_pwm_gate.rs` (renamed from `vco_phase_gate.rs`,
rewritten against hand-computed switching instants); `sig2gate_enforcement.rs` (updated to the
single-variant `GateBinding`); a new `elspice-pwl-cli` smoke test confirming both modulators'
dead-time gaps land exactly where hand-computed, plus every existing CLI test's own
`gate=off`/`gate=dutyctrl` dummy-MOSFET pattern migrated to `gate=block ctrl=<const-via-sig2gate>`.
`cargo fmt --all`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test
--workspace --release` all clean. Not yet done: migrating every `internal-archive`
experiment off the removed `gate=` spellings, and the requested LLC ZVS dead-time demonstration
experiment — both next.

## 2026-08-23 15:52 — Fixed a real `sin`/`exp` naming collision and an `expwave` `td2` default bug

Building the two follow-up demonstration experiments in `internal-archive` (an SFFM
FM-demodulator, a PULSE-driven underdamped-RLC ringing check) surfaced two real bugs in the
previous entry's own new grammar, both caught by the demonstrations actually failing to parse/
run correctly rather than assumed:

1. **`kind=sin`/`kind=exp` silently collided** with the pre-existing `MathFn1` waveform-
   arithmetic *functions* of the same names (`sin(x)`/`exp(x)` of an input signal, via the
   `MathFn1::from_name` fallback dispatch) — the new zero-input source match arms shadowed them
   entirely, so `kind=sin va=5 freq=1000` (meant as the new sinusoid source) instead produced
   "missing field 'va'" the moment anyone also had a genuine `kind=sin in=X` trig call
   elsewhere, or vice versa. Fixed by renaming all four new source kinds to `sinwave`/
   `pulsewave`/`expwave`/`sffmwave` (`pulse`/`sffm` had no actual collision today, renamed
   anyway for family consistency). New `crates/elspice-pwl-cli/tests/signal_domain_sources_cli.rs`
   locks in both the rename and, specifically, that `kind=sin` and `kind=sinwave` coexist
   correctly in one file without shadowing each other.
2. **`expwave`'s own `td2` field defaulted to `td1`** (mirroring `elspice_mna::TransientFunction
   ::parse`'s own SPICE-`EXP()`-token default), but `TransientFunction::Exp::value_at` treats
   `t < td2` as "still rising" — defaulting `td2` to `td1` (typically `0`) means *any* omitted-
   `td2` call falls straight into the *fall* phase at `t=0` instead of never falling at all,
   silently producing a curve stuck at `v1` forever instead of ever reaching `v2`. Caught by the
   FM-demodulator experiment's own dae-runtime-level and CLI-level tests both actually
   exercising a real time window, not just checking parse success. Fixed by defaulting `td2` to
   `f64::MAX/4.0` ("effectively never"), matching `pulsewave`'s own `pw`/`per` default
   convention.

`cargo fmt --all`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test
--workspace --release` all clean after both fixes (55 dae-runtime tests + 3 new
`elspice-pwl-cli` CLI-level tests, 0 failures). See `internal-archive`'s own journal
for the two demonstration experiments themselves (`elspice-pwl-sffm-fm-demodulator`,
`elspice-pwl-pulse-underdamped-rlc`) — both fully verified (the FM demod to `<1%` of a

## 2026-08-21 14:21 — Robustness Q&A, Q6: per-block RK4 vs. one fused ODE

Continuation of the "Robustness Q&A" entry below (2026-08-21 11:33, Q1-Q5) — the sixth and
last question from the user's original list, asked after a detour to commit/push every sibling
repo and set up `elspice-pwl`'s own (private) remote. Same grounding discipline as the rest of
that entry: read directly from `crates/continuous-blocks/src/state_space.rs` and
`crates/dae-runtime/src/block_graph.rs` during the session, not recalled from having written
the code.

### Q6: How do RK4-based control blocks work — does each have its own RK4, or are they all fused into one giant ODE?

**One RK4 per block, each fully independent, wired together only through already-resolved
numbers — never one fused ODE across the graph.**

Every dynamic block (`Pid`/`StateSpace`/`TransferFunction` via `StateSpace::rk4_step`; `Pmsm`
via its own bespoke `step()`) owns its state as a separate field inside its own `BlockState`
entry — `block_states: Vec<BlockState>`, one slot per `BlockInstance`, built once at the start
of a run and persisted across steps (`state_space.rs:82-93`, `block_graph.rs:561,583,591`).
Stepping one block never touches another block's state array.

What makes this correct, not just simpler, is exactly the machinery Q1/Q2 already established:

1. **`evaluate_blocks` runs blocks in `topological_order`**, so by the time any block is
   stepped, every `Signal::Block` input it needs is already a concrete number resolved *this
   step* — `input_vals` is a plain `Vec<f64>`, not a live reference into another block's ODE.
2. **`rk4_step`/`pmsm.step` hold that input vector fixed across all four RK4 stages**
   (`state_space.rs:86-89`: `k1..k4` all call `self.derivative(x_trial, u)` with the *same*
   `u`) — a zero-order hold over one circuit step, exactly what a real digital controller's own
   discrete update does (read inputs once, integrate its own state forward, done), not an
   approximation of a continuously-coupled system.
3. **Nothing needs a block's mid-step (`k1`/`k2`/`k3`) trial state — only its inputs, which are
   already fixed numbers** — so there's no possible entanglement between two blocks' RK4 stages
   the way there would be if, say, `id`'s dynamics and `iq`'s dynamics were split across two
   separate `StateSpace` blocks each needing the *other's* current-step output to compute its
   own derivative. That would be a genuine same-step algebraic loop (Q2), not solvable by any
   per-block integrator alone.

**`Pmsm` is the case worth singling out**, since its `id`/`iq`/`omega_m` dynamics are genuinely
bilinearly coupled (back-EMF/cross-coupling and torque terms mix multiple states together) —
the one place a fused treatment might seem tempting. But the fix isn't fusing `Pmsm` with
anything else: `Pmsm::step()` evaluates its *entire* nonlinear vector field (every bilinear
term) *inside one call*, so RK4's own intermediate stages naturally see the coupled dynamics
correctly, the same way any single nonlinear-ODE integrator handles a coupled system. It's
still exactly one block, one independent RK4, called once per circuit step like every other
dynamic block — the coupling lives *inside* the vector field, not *across* the block graph.

So `block_graph.rs`'s own "sampled-data co-simulation" framing is the precise description: the
block graph and the circuit are two separate discrete-time systems, each reading the other's
state at fixed sample points, and *within* the block graph, each dynamic block is its own
further-independent discrete-time system too — not one jointly-solved continuous whole.

All six of the user's original robustness questions are now answered and recorded (this entry
plus 2026-08-21 11:33). Per explicit instruction, the `book/dev-guide/` skeleton's chapters are
*not* being filled in from this yet — that's deferred to a later pass; this entry is the durable
source material for `block-graph-rk4.md` when that happens.

## 2026-08-21 11:33 — Robustness Q&A: execution order, algebraic loops, the main loop, switch resolution

Ahead of the documentation push, the user asked a series of pointed questions to verify the
simulator's robustness before trusting it enough to write it up for publication. Recorded here
in full — not just "see the conversation" — since this is the actual source material the new
`book/dev-guide/` skeleton's causality/cycle/switch-model chapters point to, and a chat
transcript isn't a durable artifact the way this journal is. Answers below are grounded in
direct code reading during the session, not memory of writing the code.

### Q1: Is execution order derived from the block diagram (computational causality)?

At the time asked: **no**. `block_graph.rs`'s own doc comment said blocks were evaluated "in
declaration order," and `Signal::Block` was documented as requiring its target to be "declared
earlier in the same slice" — a manual discipline on the netlist author, not something the
simulator computed. This was fixed in the same session (see the `topological_order` entry
above/below): execution order is now a genuine topological sort of the `Signal::Block`
dependency graph, computed once per run before any step solves. A block may now reference any
other block in the same graph regardless of declared position.

### Q2: How are algebraic loops handled — are they detected?

At the time asked: **not detected, only prevented by construction, and only diagnosed as an
opaque failure**. Because evaluation was a single forward pass building up an `outputs` map,
`Signal::Block(name)` could only ever resolve if `name` was already in that map — meaning a
same-step cycle was structurally unrepresentable, but an attempted one (or a genuine typo)
surfaced only as `DaeError::UnknownBlockInput`, which conflated "doesn't exist" and "hasn't been
evaluated yet" into one undifferentiated error. Also fixed in the same session: the new
`topological_order` uses three-color DFS marking, and a back-edge into a Gray node is
reconstructed into the *exact closing path* (`["A","B","C","A"]`) and reported as
`DaeError::AlgebraicLoop`, distinct from `UnknownBlockInput` (now genuinely only "this name
doesn't exist anywhere"). `Signal::Measure`/`Signal::BlockPrev` never contribute a dependency
edge (both read state fixed before the step starts), so they remain the sanctioned way to close
what would otherwise be a same-step loop.

### Q3: How does the main loop work?

There is no single loop — `simulate_transient` (diodes only), `simulate_transient_with_mosfets`,
and `simulate_transient_with_blocks` are siblings sharing the same per-step primitives
(`step_with_fallback`/`step_control::adaptive_step`, both wrapping `fold_and_solve`), differing
in what they rebuild each step. One step of the general (block-graph) case:

1. `evaluate_blocks`, in topological order, resolves every control block's output.
2. `resolve_gates` turns each `GateBinding` + this step's block outputs (+ `t`) into a concrete
   `GateState`.
3. Decide `forced` (must use backward Euler): first step, any gate state changed, or an active
   `RINGING_COOLDOWN_STEPS` cooldown.
4. `build_with_mosfets` rebuilds the *symbolic* `elspice-mna` system every step — a gate flip is
   a structural stamp change (switch vs. diode), not a numeric one.
5. `step_with_fallback`: if forced, solve once with `Scheme::BackwardEuler`. Otherwise try
   `Scheme::Trapezoidal` (the default, 2nd-order) first, then check the *result*: did any
   diode's resolved segment change vs. last step (`classify_segments`), or does it show
   `is_ringing` (three consecutive samples of one unknown alternating sign without shrinking —
   trapezoidal is A-stable but not L-stable, root-caused via the LLC validation example, a
   switch node ringing +/-3000V through MOSFET dead time)? Either one discards the trapezoidal
   trial and redoes the step with backward Euler, then starts a 3-step forced-backward-Euler
   cooldown (one corrective step isn't enough to re-satisfy trapezoidal's own "needs consistent
   initial conditions" requirement).
6. Update bookkeeping (`prev_segments`, `prev_gate_states`, `prev_diode_raw_ioff` for next
   step's trapezoidal history term), shift `x_prev_prev <- x_prev <- point.x`, push the step.

Adaptive-`dt` mode wraps the same `fold_and_solve` core in a local-truncation-error-controlled
loop instead — a separate mechanism layered on top, not a different core.

### Q4: We have switches with PWL regions — how does the "switch manager" monitor the need for switching?

Two genuinely different mechanisms, not one:

- **MOSFET gate on/off is not monitored at all.** `pwl_devices::Mosfet`'s own doc comment is
  explicit: gate state is "an external, exogenously-known control input... not a modeled `Vgs`
  compared against a threshold anywhere in this crate." The caller (PWM comparator, block-graph
  `GateBinding`) decides it entirely outside the DAE/LCP machinery. Given a known state,
  `build_with_mosfets` picks one of two *structural* stamps: on -> plain linear switch (`r_on`,
  no complementarity variable at all), off -> body diode folded into the diode LCP.
- **Diode/body-diode segment selection is genuinely endogenous, resolved by one simultaneous
  solve, not per-device polling.** Every diode gets 2 complementarity pairs (`w1,z1` guarding
  breakdown, `w2,z2` guarding the forward threshold); *all* diodes in the circuit are stacked
  into one `(M,q)` LCP and solved in a single Lemke pivoting pass — the `gamma[k][j]`
  cross-coupling terms make this genuinely simultaneous across every diode at once, the same way
  real KCL/KVL are simultaneous. `classify_segments`, run *after* the solve, only reads off
  which `z` came back nonzero — used for the backward-Euler-fallback bookkeeping in Q3, not part
  of finding the segment.

### Q5 (challenge): Is it not better to bring MOSFET switching into the same LCP/DAE scheme too?

A real design question, answered "no, and here's the principled reason, not just current
scope":

- **The math**: the diode LCP works because every segment of a diode shares one *fixed
  reference conductance* `g_off` — segment choice only ever shifts an affine current-source
  term at *fixed* topology, keeping the linear system `A0` genuinely fixed regardless of `z`
  (see `lib.rs`'s own module doc comment, "The generic Thevenin/LCP fold"). A MOSFET channel
  going from closed to fully open is not that kind of change — it's the literal
  appearance/disappearance of a conductance path, a *topological* change to `A0` itself. That's
  exactly why `build_with_mosfets` rebuilds the symbolic system rather than folding switch
  state into the same fixed-`A0` LCP diodes share; the algebraic trick the diode fold depends on
  doesn't apply.
- **The physics, independent of the math**: in every circuit this crate targets (PWM power
  converters), the gate signal genuinely *is* an externally-commanded control input in the real
  system too. A real gate driver doesn't discover it should switch by solving a complementarity
  condition on `Vgs` vs. `Vth` — a controller commands it directly. Treating it as exogenous is
  model fidelity to how these systems actually work, not a shortcut around a harder problem.
- **Where the question does point at something real**: a genuinely self-triggering ideal switch
  (a relay, a fuse, a MOSFET operated with no active gate signal at all, pure natural
  commutation) — state genuinely should be resolved from circuit state there, but it would
  still need its *own* formulation (same topology-change problem), not simple insertion into
  the diode `M`/`q`. Recorded as an open extension point (`book/dev-guide/src/open-questions.md`),
  not implemented — the user agreed this is a different, real feature rather than "the same
  thing done better," and asked to move on rather than build it now.

## 2026-08-20 13:45 — `Mosfet` body-diode node order flipped to plain SPICE `(drain, source)`

Surfaced by the TIDA-010954 cycloconverter experiment's own instability investigation
(`internal-archive`'s Phase 5): after fixing a phase-shift sign bug and bumping
near-zero ESR values, `I(Vac)` still diverged exponentially. Standalone body-diode testing
(the standard SPICE approach — gate held off, forward/reverse DC sweep through a series
resistor) confirmed the real cause: `pwl_devices::Mosfet`'s own doc comment required netlist
nodes declared `(source, drain)` — the *opposite* of the universal SPICE `(drain, source)`
convention — and 6 of that experiment's 8 MOSFETs were declared the natural, SPICE-conventional
way, giving every one of them a backwards body diode.

Rather than just re-documenting the requirement (the user's own framing: "so I won't miss it
again"), fixed the contract itself. Added `Diode::reversed()` (`crates/pwl-devices/src/
diode.rs`): the same physical diode with its two terminals swapped, satisfying `reversed()
.current(v) == -self.current(-v)` for every `v` — derived by substituting `u=-v` into each of
the 3 segments, which turns out to be exactly `Diode::new(g_on, -v_th, g_off, -v_breakdown,
g_breakdown)` (swap `g_breakdown<->g_on`, negate+swap `v_breakdown<->v_th`) — verified both via
that algebraic identity (sampled across every segment) and a concrete physical check against
the TIDA MOSFETs' own parameters. `Mosfet::body_diode_for_drain_source_stamping()` returns
`self.body_diode.reversed()`; `dae-runtime::build_with_mosfets` now calls this instead of using
`body_diode` directly, and the netlist convention is now plain `(drain, source)`.

Also corrected `Mosfet`'s own doc comment, which had the physics slightly wrong: channel on/off
depends only on `Vgs` vs `Vth`, not on the sign of `Vds` — a real MOSFET's channel, once on,
conducts in both directions almost symmetrically (synchronous rectification exploits exactly
this: the channel carries the freewheeling current at a much lower drop than the body diode
would, for `Vds<0` too, as long as the gate is still on). So it's "gate on → switch behavior
for *any* `Vds`," and "gate off → body-diode-only behavior for *any* `Vds`" (blocking when
`Vds>0`, conducting when `Vds<−Vf`) — not two `Vds`-conditioned regimes. Also confirmed and
documented that gate state is genuinely exogenous in this crate (decided by `dae-runtime`'s
PWM/controller logic before the circuit is even built) — there is no modeled `Vgs` node or
threshold comparison happening inside the MOSFET's own curve anywhere.

**Breaking change to `pwl-devices`' public contract**, deliberately, not an accretive addition:
4 existing tests (`dae-runtime`'s `mosfet.rs`, `pwm_mosfet_transient.rs`, `vco_phase_gate.rs`,

--all-targets --examples -D warnings`/`test --workspace --release` clean after the fix.

## 2026-08-20 11:34 — Wire `elspice-mna`'s new time-varying sources into the transient loop

`elspice-mna` grew `SIN`/`PULSE`/`EXP`/`PWL`/`SFFM` source support this session (see its own
`docs/journal/2026-08.md`, 2026-08-20 07:49): a `V`/`I` element with a recognized transient
function is stamped as a symbol, not a baked literal, and `MnaSystem::transient_sources` maps
that symbol's name to a `TransientFunction` whose `value_at(t)` the *caller* is responsible for
sampling every step. `elspice-mna` deliberately has no notion of "now" — that's this repo's job.

This crate's entire transient call graph had no notion of absolute simulated time at all
before today, only relative `dt` — `fold_and_solve`, `step_with_fallback`,
`step_control::lte_attempt`/`adaptive_step` all needed `t: f64` threaded through as an explicit
new parameter (11 call sites across `lib.rs`, `step_control.rs`, `block_graph.rs`,
`closed_loop.rs`). Convention settled on: `t` passed to `fold_and_solve`/`step_with_fallback` is
the step's own (new) absolute time; `t_start` passed to `lte_attempt`/`adaptive_step` is the

each attempt; `Scheme::Dc` always uses `t=0.0` (matches SPICE convention: DC operating point
uses a transient source's value at time zero). `fold_and_solve` now injects
`transient_fn.value_at(t)` into `base_values` for every entry in `system.transient_sources`
before calling `system.evaluate` — zero cost, zero behavior change, for the (still-common) case
where that map is empty.

**Found and fixed a real, previously-invisible latent bug while wiring this up**: the
`Scheme::Trapezoidal` branch's own doc comment already correctly derived the RHS as
`(B/2)*(u_n + u_{n+1})` (source values averaged at both endpoints) but the *code* used
`B*u_{n+1}` alone — a shortcut the same doc comment explicitly flagged as relying on every
source being constant "in this crate's scope," which was true until today. Invisible until now
because `u_n == u_{n+1}` trivially for a constant source. With a real `SIN` source, this
manifested as pathological adaptive-step behavior: `err≈231` from the very first attempt,

`2*u(t_new) - u(t_prev)` exactly, while the correct backward-Euler comparison matched
`10*sin(2*pi*50*t)` exactly, confirming the averaging omission by hand rather than guessing.

non-empty) and average it with `numeric0.u` in the effective RHS. Verified: the same `SIN`
circuit's adaptive run dropped from hanging to 0.104s / 1275 steps for the full 20ms, matching
`10*sin(2*pi*50*t)` to machine precision (~1e-14–1e-15) at spot-checked times.

## 2026-08-19 13:43 — `cscript-ffi`: dynamically-loaded, user-supplied C blocks (`kind=cscript`)

New crate `crates/cscript-ffi`: loads a user-precompiled shared library (`.so`/`.dylib`/`.dll`
— the user compiles it themselves with their own `cc`/`gcc`; this project never invokes a
compiler) exporting `cscript_start`/`cscript_output`/(optionally) `cscript_free`/
`cscript_clone`, and calls into it once per block instance — an escape hatch for block behavior
none of `continuous-blocks`'s own blocks cover, deliberately allowing genuine state (an
integrator, a lookup table built at `cscript_start`, anything), unlike every stateless
`waveform_arithmetic` function. This is the one place in the whole workspace where calling into
arbitrary native code is allowed at all — documented as such directly in the crate's own module
doc comment, not hidden.

Two real design problems, both caught and fixed before this reached `dae-runtime`:

- **Multi-instance state.** Two block instances naming the same `lib=` path share one
  `dlopen`'d image (a `CScriptRegistry` caches by path), but each gets its own
  `cscript_start()` call and its own opaque state pointer — verified with a real two-instance
  test (`two_instances_of_the_same_library_keep_independent_state`), not just asserted.
- **Adaptive step-size control clones `block_states` before every trial** (see the adaptive
  step-size control entry above) — a plain `Vec<f64>` clone is a real independent copy, but an
  opaque C state pointer can't be generically deep-copied without help. Added an optional
  `cscript_clone` symbol to the contract; `Clone` for `CScriptInstance` calls it and panics if
  absent, but `dae-runtime` checks `supports_clone()` *before* ever entering the adaptive path
  and returns a clean `DaeError::CScriptRequiresCloneForAdaptiveStep` instead — the panic exists
  as a documented backstop, not a real user-facing failure mode.

Also added, after being asked directly whether a C block's execution rate could be set
independent of the circuit's own step (as it is in every other tool with this kind of scripting
slot) and realizing the answer was no: `sample_time` (`ts=<seconds>`/`freq=<hz>` at the CLI).
`cscript_output` only actually runs once accumulated circuit time reaches the configured period,
holding its last output (zero-order hold) on every step in between, and receives *that*
accumulated period as its own `dt` argument — not the circuit's own much finer step. Caught a
real bug while wiring this in: the first-ever call used an `f64::INFINITY` sentinel for "never
sampled yet" so it would always fire, but `infinity + dt` stays infinite, poisoning that first
call's `dt` and corrupting any block that integrates (`s->integral += error * dt` immediately
became `inf`) — fixed by seeding `time_since_sample` at `sample_time` itself instead (finite,
still always due, no corruption).

`dae_runtime::block_graph`: `BlockKind::CScript { lib, output_names, sample_time }` (more than
one `output_names` entry registers extra named outputs alongside the block's own primary name,
so a C block can produce several signals from one call, e.g. a control output plus an internal
diagnostic like an integrator's own accumulator); `BlockState::CScript` carries the live
instance plus the zero-order-hold bookkeeping. `elspice-pwl-cli`: `kind=cscript lib=<path>
[in=<signal> | inputs=<signal>,...] [outputs=<name>,...] [ts=<seconds> | freq=<hz>]`.

Verified end to end three ways: a manual scratch smoke test (a real PI controller compiled as a
`.so`, closing a buck voltage loop, sampled at 40kHz independent of a 100kHz switching carrier —
regulated correctly once the infinity bug above was found and fixed); a permanent regression
suite (`crates/elspice-pwl-cli/tests/cscript.rs`, 3 tests against the real built binary and real
compiled `.c` fixtures: exact-value stateless gain, sample-time zero-order-hold row-counting,
and the missing-`cscript_clone`-under-adaptive-step error path); and `cscript-ffi`'s own 7 unit
tests (load/call/free lifecycle, multi-instance independence, clone correctness and its
documented panic path). `cargo fmt`, `cargo clippy -D warnings`, `cargo test --workspace
--release` all clean across the whole workspace.

Not yet built (explicitly out of scope for this pass, noted for whenever the TIDA-010954
digital controller is actually reproduced): nothing else — `sample_time` was the one piece asked
for ahead of time and is done.

## 2026-08-19 12:30 — `Hysteresis` block + `gate=block` binding, for bang-bang current-mode control

Added a `Hysteresis` block (`crates/continuous-blocks/src/hysteresis.rs`, mirroring `Vco`'s
pattern: a small standalone struct with a `.step(prev_state, x) -> bool` method, unit-tested
against hand-derived truth-table cases) — a Schmitt-trigger comparator: stays on until the
input drops below `low`, stays off until it rises above `high`. Deliberately not a `StateSpace`
(the on/off memory is a genuine discrete latch, same reason `Vco`'s `[0,1)` wraparound is
handled directly rather than folded into one).

Wired into `dae_runtime::block_graph`: new `BlockKind::Hysteresis`/`BlockState::Hysteresis(bool)`
pair, plus a new `GateBinding::Block(String)` variant — on while the named block's current
output is `>=0.5`, no carrier at all (unlike `GateBinding::Pwm`'s fixed-frequency comparator).
Needed because bang-bang/hysteresis control has no fixed switching frequency to compare a duty
command against — the switch state *is* the block's own output, directly. `elspice-pwl-cli`:
`kind=hysteresis high=<f64> low=<f64> in=<signal>` and `gate=block ctrl=<block-name>`.

Verified end to end in `internal-archive/experiments/elspice-pwl-buck-hysteresis-current-mode/`:
a hysteresis-controlled buck (no duty/PWM at all) reproduces the standard current-mode result —
`I(L1)` rides a sawtooth band tight against the designed `+-0.5A`, `V(vout)` self-regulates to
`I_ref * R`, measured switching period (17.4us) matches a hand-derived estimate from the
inductor's on/off `di/dt` slopes almost exactly. Also surfaced a genuine limitation of the
just-added adaptive step-size control: its LTE estimator is tuned to the *continuous* LC
dynamics and has no way to anticipate a discrete hysteresis-threshold crossing mid-step, so the
adaptive run's ripple band measurably overshoots the fixed-dt result (~1.9A vs. ~1.1A
peak-to-peak, nominal design 1A) — not a bug, but a real architectural tradeoff worth knowing
about before relying on adaptive stepping for bang-bang-controlled circuits. `cargo fmt`,
`cargo clippy -D warnings`, `cargo test --workspace --release` all clean.

## 2026-08-19 12:17 — Adaptive (local-truncation-error) step-size control, alongside fixed-step

Every transient function in this crate used a fixed, caller-given `dt` for the whole run,
uniformly — no adaptivity at all. Added the alternative: new `dae_runtime::TimeStep` enum
(`Fixed(f64)` — exactly the old behavior, unchanged — or `Adaptive(AdaptiveConfig)`), and a new
`step_control` module implementing local-truncation-error step-size control, the same general
idea every real SPICE-family tool uses by default:

- **Error estimate**: solve the *same* trial `dt` with both backward Euler (order 1, `O(h^2)`
  local error) and trapezoidal (order 2, `O(h^3)` local error); their difference is dominated
  by backward Euler's own larger error term, giving a cheap, history-free proxy for
  trapezoidal's actual error — the same idea an embedded Runge-Kutta pair (Runge-Kutta-
  Fehlberg) uses two different-order formulas for, adapted to the two schemes this crate
  already implements instead of introducing new ones.
- Normalized against `abstol + reltol*max(|x_trap|,|x_be|)` per unknown (the standard
  `RELTOL`/`ABSTOL` idea), accept/grow (`dt *= clamp(sqrt(1/err),0.2,5.0)*0.9`) or
  reject/shrink (`dt *= clamp(sqrt(1/err),0.1,0.5)`, retry at the same `t`) against `err<=1`.
  A segment/gate change or detected ringing still forces backward Euler outright (same policy
  `step_with_fallback` already had), with `dt` conservatively halved afterward rather than
  trusted to the error estimate.
- `simulate_transient` (no MOSFETs, `system` fixed for the whole run) owns a plain retry loop
  directly on top of the new `lte_attempt` primitive. `simulate_transient_with_blocks` can't
  reuse that loop as-is: its `system` is rebuilt from block outputs that are themselves a
  function of `dt` (gate states depend on the block graph, which is stepped at `dt`), so a
  rejected trial has to redo block evaluation *and* gate resolution at the smaller `dt`, not
  just re-solve the same system. Factored the per-step block-evaluation logic out into a
  reusable `evaluate_blocks`/`resolve_gates` pair (used by both the fixed and adaptive
  branches) and gave `BlockState` a `Clone` impl so a rejected adaptive attempt's block-state
  advance can be discarded and retried from a clone, without corrupting the real state.
- `elspice-pwl-cli`: `--dt` still fixes the step (unchanged, deterministic, exactly
  reproducible). Omit it — the new default — for adaptive control, with
  `--dt-max`/`--dt-min`/`--dt-init`/`--reltol`/`--abstol` overriding `AdaptiveConfig::
  from_t_final`'s own defaults (`dt_max=t_final/1000`, `dt_init=dt_max/100`,
  `dt_min=dt_max*1e-9`, `reltol=1e-3`, `abstol=1e-9`) piecemeal. `--dt` and any `--dt-*`/
  `--reltol`/`--abstol` flag are mutually exclusive (checked, clear error message).

Verified: fixed-step results are bit-for-bit identical to the pre-change baseline (re-checked
the boost open-loop deck's known trace). Adaptive mode on the underdamped-buck closed-loop
deck (`dt_max=1e-6`, 10x the fixed `dt=1e-7` used for that deck previously): **1.37s and
40,622 points, vs. 6.5s and 350,000 fixed points for the same 35ms run** — roughly a 4.7x
wall-clock speedup and 8.6x fewer points — while reproducing the same overshoot/settling shape
(peak ~16.0V vs. fixed-step's ~15.2V, settled averages 11.56V/8.95V vs. 11.84V/8.99V, both
comfortably within what different-but-consistent tolerance-driven step selection should give).

`cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets --examples -- -D
warnings`, `cargo test --workspace --release` all clean.

## 2026-08-17 10:55 — Closed-loop `continuous-blocks` wiring: a real PID+PWM+MOSFET regulator

Added `dae_runtime::simulate_closed_loop` (new `closed_loop.rs` module, `continuous-blocks`
now a real dependency of `dae-runtime`, not just standalone): a `continuous_blocks::StateSpace`
controller (a compiled `Pid`) drives a circuit's MOSFET gate(s) via a caller-supplied PWM
comparator. Deliberately a **sampled-data co-simulation**, not a fully implicit unified
system — the controller reads the previous step's measured output, steps its own RK4
integrator, and the result decides this step's gate states before the circuit step is solved.
Documented explicitly as not a shortcut: this is literally how a real digital PID+PWM
controller works (sample, compute, update at discrete instants), not an approximation of a
"more correct" implicit approach. This is the payoff the original plan described: a PID
controller driving a switching gate with no Xyce-style `tanh`-smoothed comparator needed (see
`gotchas/xyce-pid-timestep-collapse-needs-smooth-comparator.md` in the knowledge-base repo),
since gate switching here is just another LCP-resolved mode, never a Newton convergence hazard.

Hit and fixed two real bugs while building the first verification fixture (not code bugs —
circuit-design mistakes on my part, working as designed once caught):

1. **First circuit topology was fundamentally wrong.** A MOSFET's body diode conducts
   source-to-drain *unconditionally*, regardless of gate state. My first test circuit (V1 --
   MOSFET(source=input,drain=output) -- RC) had the body diode's forward direction matching the
   circuit's own normal charging direction, so it kept conducting even with the gate off,
   defeating the switch entirely — the "OFF" state offered essentially no blocking, and the
   output just charged monotonically toward the input voltage regardless of duty cycle. Fixed
   by reversing the MOSFET's netlist node order (`(drain, source)` for a topology where the
   switch needs to block current flowing *into* the load) so the body diode's forward
   direction opposes normal operation instead of matching it — the correct orientation for a
   high-side chopper switch with no inductor.
2. **Wrong intuition about the averaged input-output relationship.** Assumed the classic buck
   converter's `V_out ~= duty * V_in`, which only holds with an inductor. This topology (no
   inductor, load resistor comparable to `Ron`) actually averages to
   `V_out ~= duty * V_in / (duty + Ron/Rload)` (derived by hand once the first open-loop test's
   result at duty=0.6 didn't match `duty*Vin` even after fixing bug 1) — caught immediately
   because the discrepancy was large and consistent, not close-but-off. The naive relationship
   is now used only to sanity-check the reference is *reachable*, never as a pass/fail
   criterion.

After both fixes, the closed loop genuinely regulates: verified in
`tests/closed_loop_pi_regulator.rs` by the standard, well-established control-theory property
that integral action drives steady-state error to zero for a step reference — checked as a
wide-window average (half the simulated run, not just the last couple of switching periods,
since this sampled-data loop settles into a bounded oscillation around the reference rather
than a tight DC value, an expected consequence of measuring the rippling PWM node directly at
a fixed `dt` rather than synchronously with the switching period) plus a sanity check that the
duty command settled to a real, non-saturated value. Explicitly does **not** attempt to verify
the exact switching transient by hand — not a gap specific to this project; that's true of
switching converters in general.

## 2026-08-17 10:42 — Full trapezoidal integration, closing the deferred Milestone 6 gap

Implemented `Scheme::Trapezoidal` alongside the existing `BackwardEuler`/`Dc` schemes.
Derivation: summing the descriptor DAE at `t_n` and `t_{n+1}` and using the trapezoidal
relation `x'_n + x'_{n+1} = (2/dt)(x_{n+1}-x_n)` to eliminate the derivatives entirely gives
`(A/2 + K/dt) x_{n+1} = (B/2)(u_n+u_{n+1}) + (K/dt - A/2) x_n` — the same linear-solve shape
every scheme so far has used. The one real subtlety: `B u` includes each diode's *nonlinear*
current, and true trapezoidal accuracy requires averaging that too, not just the netlist's own
constant sources — so the new step's diode current contributes only `(B/2)*raw_Ioff_{n+1}` (a
new `coupling_scale` factor threaded through the LCP fold's coefficients), while the *previous*
step's already-known current contributes its own `(B/2)*raw_Ioff_n` directly to the effective
RHS. Added `OperatingPoint::diode_raw_ioff` (each diode's true unscaled resolved current) so
`simulate_transient` can carry that history forward without every caller having to recompute it.

This derivation assumes `x_n` already satisfies the circuit's algebraic constraints exactly —
true right after a backward-Euler step, not from an arbitrary `x_initial`. This is the DAE
analog of "trapezoidal needs consistent initial conditions," and is why `simulate_transient`
now always starts with backward Euler, then uses a lagging policy for every later step: try
trapezoidal, and if the resolved diode segments (breakdown/leakage/forward) differ from the
previous step's, redo that step with backward Euler instead — matching the architecture's own
stated policy of falling back to backward Euler immediately after an LCP-resolved mode change.

Verification: rather than compare absolute errors at one `dt` (which depends on unknown,
method-specific constants and can mislead), checked the actual *convergence order* by halving
`dt` — the standard, rigorous way to verify a method's order. Backward Euler's error roughly
halved (ratio 1.7-2.3, confirming first-order); trapezoidal's roughly quartered (ratio 3.0-5.5,
confirming second-order) — both against the same closed-form RC exponential used in Milestone
6's original fixtures. This lives in a `#[cfg(test)] mod scheme_tests` inside `src/lib.rs`
itself, since `Scheme`/`fold_and_solve` are intentionally private. Also tightened
`tests/transient.rs`'s existing RC fixtures' tolerances from `5e-3` (sized for first-order
backward Euler) to `1e-5` (500x tighter) now that trapezoidal is the default through the public
`simulate_transient` API — both still pass, real evidence the accuracy upgrade reaches actual
callers, not just the internal convergence-rate test.

`cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets -- -D warnings`,
`cargo test --workspace` all clean (38 tests total across the workspace).

## 2026-08-17 10:30 — Milestone 6 (transient timestep loop) complete, backward Euler only

Added `dae_runtime::simulate_transient`: a backward-Euler timestep loop over the same
diode/LCP fold Milestones 2-4 already built. The generalization turned out clean rather than
requiring new machinery: on a descriptor DAE `A x + K dx/dt = B u`, backward Euler's
`dx/dt ~= (x_{n+1}-x_n)/dt` gives `(A + K/dt) x_{n+1} = B u_{n+1} + (K/dt) x_n` — exactly the
same linear-solve shape `solve_dc` already used, just with an effective matrix/RHS instead of
the plain algebraic ones. `fold_and_solve` was refactored to take an optional
`(x_prev, dt)` step context and compute that effective matrix/RHS once, up front; every
diode/LCP-fold line after that is unchanged, since it only ever depended on "the effective
matrix" and "the effective baseline RHS," not on what those actually are. A row with no
storage element has a zero `K` row, so it reduces to the plain algebraic equation there
automatically — no special-casing dynamic vs. algebraic rows anywhere.

Deliberately backward-Euler only, not full trapezoidal (documented as a scope choice, not a
silent gap, in `simulate_transient`'s own doc comment): trapezoidal needs each step to also
carry forward the previous step's `dx/dt`, more bookkeeping backward Euler doesn't need, and
backward Euler is already the architecture's own sanctioned choice immediately after every
LCP-resolved mode change — for a circuit whose PWL devices switch segments often, that may be
most of the time anyway. Also deliberately diodes-only for now (no MOSFET/PWM transient
variant): a time-varying gate signal is real additional scope (a controller/PWM driver) not
needed to prove the core "re-resolve the LCP every timestep" mechanism actually works over
time, which is the actual point of this milestone.

Verification, three fixtures in increasing combined complexity (`tests/transient.rs`):
1. A purely algebraic circuit (Milestone 3's exact two-diode fixture, no storage) has `K = 0`
   everywhere, so the backward-Euler fold should reduce to the *exact* already-verified DC
   answer at every single step, immediately — not an approximation converging toward it. Held
   at every one of 5 steps.
2. A plain RC charging circuit (no diode) against its closed-form exponential
   `Vc(t) = 5*(1-e^-t)` — checks the integrator itself, independent of any PWL device.
3. An RC circuit charging *through* a forward-biased diode — combining both mechanisms in one

   diode's resolved segment (forward-conducting, not off or in breakdown) checked at every
   sampled point too.

## 2026-08-17 10:16 — Milestone 4 (`Mosfet` model) complete, zero further `elspice-mna` changes

Implemented the MOSFET spec (controlled bidirectional conduction when gated on; body-diode-only
"natural, circuit-driven" conduction when gated off) by **decomposing it into two mechanisms
that already existed** rather than inventing a new device type end to end:

- Gated on: the channel conducts both directions, i.e. it's just a plain resistor — reuse
  `elspice-mna`'s existing switch (`Ron`/`Roff`) mechanism directly.
- Gated off: the intrinsic body diode conducts only if pushed backward — reuse the `'D'` stamp
  and the LCP fold from Milestones 2-3 unchanged, giving it `pwl_devices::Mosfet::body_diode`
  (an ordinary `Diode`).

Which mechanism applies per instance per timestep is an *exogenous* gate command (from a
controller/PWM), not something the LCP resolves — so `dae-runtime::solve_dc_with_mosfets`
just partitions its `mosfets` map at build time: gated-on names become `BuildOptions` switch
overrides, gated-off ones get merged into the same `diodes` map Milestone 3 already folds.
Required **no further `elspice-mna` changes** — both mechanisms it needed were already there.

The one real design decision: getting the body diode's polarity right (conducts when
`V_source > V_drain + Vf`) by reusing `Diode` completely unchanged, via a *node-order*
convention — a `Mosfet` element's two netlist terminals must be `(source, drain)`, documented
on the struct itself. A plain resistor doesn't care about terminal order, so this costs
nothing in the gated-on case.

Hit one real environment fact while writing the first test: `spice-core` enforces actual SPICE
grammar per device letter, and rejected a 2-node `M1 ...` line ("device Mosfet requires at
least 4 nodes"). Since this simulator's MOSFET is deliberately 2-terminal (gate is an
