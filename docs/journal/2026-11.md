## 2026-11-27 15:13 — 0.11.0: a parameterised `.subckt` runs

[#140](https://github.com/GLODI-Engineering/general-simulator/issues/140). This binary could
not run a parameterised subcircuit at all. Both halves of the grammar parsed — the definition's
formal list and the `X` card's `name=value` tail — and nothing bound them, so the body's `{Rv}`
arrived at the builder as the name of a parameter nothing declared:

```
error: Evaluate(MissingSymbol): evaluating an expression failed: missing value for symbol 'Rv'
```

A top-level `.param Rv=330` had always solved, so the evaluator and the symbol table were never
the problem — only the scope was. The repair is
[general-mna#63](https://github.com/GLODI-Engineering/general-mna/issues/63), in
`hierarchy::flatten`, which is where node scoping already lives; this release carries it
through the path dependency.

**Nothing in these crates changed except their versions**, which is exactly why the test
matters. A capability that arrives through a dependency has no evidence in the repository that
ships the binary unless something here asserts it, and the failure mode is not a crash: a
binding pass that fell back to the declared default would produce a complete, plausible run of
a circuit nobody wrote. So `subckt_parameters_cli.rs` asserts the numbers the deck implies —
$5/320\,\mathrm{A}$ through the source and $5 \times 220/320\,\mathrm{V}$ at the mid-node,
derived rather than recorded — and then asserts that the all-defaults circuit's numbers
($2.5\,\mathrm{mA}$, half-divided) are *not* what came out.

Watched failing first: with `general-mna`'s `src/hierarchy.rs` restored to its pre-#63 state,
both tests fail with the message above. That is the only check that proves the test covers the
dependency rather than the fixture.

The netlist grammar chapter documented the hierarchy and said nothing about parameters; it now
states the four scoping rules and the three refusals.

**Ordering, because it reaches two other repositories.** `general-mna` moves to 0.11.0 with
this release for the reason it always does — it requires `continuous-blocks` and `pwl-devices`
by version as well as by path. And `gsim-core` must *not* start emitting subcircuit parameters
until this release is out: a deck carrying `Rv=100` into a solver that drops it parses cleanly
and loses the value one repository further down, which is worse than refusing. That rule is
written into `gsim-core`'s decision 0010.

## 2026-11-06 06:13 — `#21` is wrong; what is real is the `phys2sig` sampling delay

**Asked:** solve the open bugs. `#21` claimed *every* CSV row's values are one $\Delta t$ behind
that row's own timestamp, which would bias every windowed measurement in the project.

**Found: the claim does not reproduce, and I filed it.** Measured, not argued:

- A 50 Hz `SIN()` source run at `--dt 1e-4` gives `V(vac_node)` equal to
  $A\sin(2\pi f t)$ at the row's own stamp to full printed precision — not
  $A\sin(2\pi f (t-\Delta t))$, which the issue asserted matched "to every printed digit".
- The same sinusoid as a `kind=sinwave` *block* agrees with the source column row for row, so
  the circuit solve and the block graph share the same stamp.
- The `pulsewave` edge that prompted the report (`pw=6e-6`, `--dt 1e-7`) is correct. The last
  high row is stamped `5.999999999999995e-6` — accumulated float addition, *below* 6 µs, where
  the gate is genuinely still high. Reading that as "6e-06" is what produced the report. It is
  a one-line mistake that a glance at the printed digits does not catch.

**What is real, and narrower.** `kind=phys2sig` reports the circuit as of $t-\Delta t$, and `0`
in the first row, because `evaluate_blocks` is handed `point_prev` — the block graph must be
evaluated before the circuit is solved, since a block's output can decide a gate state or a
source magnitude for the step about to be solved. Deliberate, and already documented in
`book/dev-guide/src/block-graph-descriptor.md`, `docs/architecture.md`, and the module doc
comment. Already asserted per-step by `crates/dae-runtime/tests/phys2sig_block.rs`.

So the behaviour was tested and designed; the gap was that **no user-facing page said it, and
the component reference said the opposite** — "`PROBE1` tracking `V(out)` exactly", with
`doc-verify/phys2sig` asserting that on the *last* row of an already-settled divider, where it
is true. A settled circuit hides the delay after row one.

**Changed.**

- `crates/dae-runtime/src/block_graph.rs`: the `Phys2Sig` match arm is now a named, documented
  `phys2sig_value`, carrying a `<!-- doc-ref: phys2sig -->` implementation note. That tag is how
  this repo adds to a component entry whose primary doc comment lives in `general-mna`, which is
  a read-only path dependency here.
- `book/user-guide/src/reading-output.md`: new "What time a row's values belong to" — the first
  row is $t=\Delta t$ (which `measurements.md` already linked here for and this page did not
  have), every column is the row's own $t$, and the one `phys2sig` exception with its verified
  output.
- `book/user-guide/src/signals.md`: its `prev:PROBE` example already *showed* `PROBE=0` while
  `V(b)=2.5` and said nothing about it. It now says `DELAY` ends up two steps behind the
  circuit, and which step belongs to which mechanism.
- `crates/general-simulator-cli/tests/csv_row_time_alignment.rs` (new, 4 tests): pins both
  halves — no global offset, and the probe's offset is exactly one step — so a fix aimed at
  either claim cannot silently break the other.
- `doc-verify/phys2sig`: runs the same netlist a second time at a coarse `dt` and asserts the
  per-row relation, instead of only the settled last row.
- `docs/gotchas/GOTCHA-002`: both traps that let this survive — the settled-circuit check, and
  the fact that near a sinusoid's peak $\sin(t)\approx\sin(t-\Delta t)$ so a spot check cannot
  tell a one-step shift from none. The second is exactly what produced the wrong diagnosis.

**Not changed.** The delay itself. `docs/architecture.md` records it as a deliberate choice and
`book/dev-guide/src/design-decisions.md` names what would have to be true to revisit it; that is
a design question, not a bug fix. `general-mna`'s own `Phys2Sig` doc comment still says the
example "tracks `V(out)` exactly" — correcting it there needs explicit confirmation first
(`AGENTS.md`, project boundaries), so the implementation note names the caveat directly below it
in the generated entry.

**Verification.** `cargo fmt --all -- --check`, `cargo clippy --all-targets -- -D warnings`,
`cargo test --workspace` (62 suites, 0 failures), `python3 doc-verify/phys2sig/test_phys2sig.py`
(7/7), `mdbook build book/user-guide/` with KaTeX confirmed rendering the new math.

## 2026-11-25 16:55 — A gate change got one backward-Euler step, and a smaller step made it worse

Issue #113: a node held by a conducting body diode sat tens of volts outside its clamp, and the
time it spent there grew as `--dt` shrank. That direction was the whole clue — a trapezoidal
overshoot shrinks with the step — and it pointed away from the integrator and toward segment
selection, which is where the report's own suspicion sat too.

It was neither. The LCP is innocent: an audit of every solve in a reproducing run found no
complementarity violation anywhere (`w = Mz + q` to $10^{-6}$, `w, z >= 0`, `w . z = 0`), so
every accepted step *did* satisfy the diode's own clamp. The excursion came from a few steps on
which trapezoidal was trusted when it should not have been.

`step_with_fallback`'s doc comment says the backward-Euler cooldown follows "any backward-Euler
fallback (not just a ringing-triggered one — a segment or gate change deserves the same settling
courtesy)". The code said `used_backward_euler && !forced`, and `forced` is exactly the two
reasons known before solving: the first step of a run, and a gate change. So the two mode
changes imposed from outside the solver were the two that got one corrective step and nothing
more. All five transient loops had copied the same expression, so all five were wrong
identically — `next_ringing_cooldown` now holds the policy once and they call it.

Why one step is not enough, and why less so at a smaller step: the stiff mode is
$\tau = R_{on} C_{node}$, $7\ \mathrm{ps}$ for $0.021\ \Omega$ and $348\ \mathrm{pF}$. Backward
Euler kills it in one step when $\Delta t \gg \tau$ and proportionally less as $\Delta t$
approaches $\tau$, while trapezoidal's factor
$(1 - \Delta t/2\tau)/(1 + \Delta t/2\tau)$ sits just inside $-1$ there. A smaller step leaves
more residual to a scheme that will not damp it. `is_ringing` cannot catch the result because
it tests the sign of the raw unknown and this oscillation is about a $400\ \mathrm{V}$ rail,
never crossing zero — it was written against a dead-time node swinging about zero, which does.
That blindness is now issue #116, not a change smuggled into this fix: the offset-invariant
signature is sign alternation of the increments, and three samples cannot tell that from one
turning point of a smooth waveform.

**Reproducing it without the reporting netlist.** The report's two non-reproducing circuits both
held their gates off; adding gates that actually switch to a single textbook half-bridge leg was
enough. Which step size shows it depends on $\tau$, so the fixture
(`crates/dae-runtime/tests/body_diode_clamp.rs`) is a three-leg bridge with $174\ \mathrm{pF}$,
$1.65\ \mathrm{nF}$ and $16.5\ \mathrm{nF}$ across each switch — three decades of $\tau$, so a
different leg misbehaves at each step size and the test fails at all three.

| `--dt` | peak before (clamp $401\ \mathrm{V}$) | peak after |
|---|---|---|
| 5 ns | 427.9 V (leg c) | 402.0 V |
| 0.5 ns | 428.1 V (leg b) | 402.4 V |
| 0.05 ns | 428.1 V (leg a) | 402.4 V |

and the troughs $-25.9\ \mathrm{V}$ and $-13.8\ \mathrm{V}$ against a $-1.0\ \mathrm{V}$ clamp
become $-2.3\ \mathrm{V}$ at worst. The same node's peak now varies by under $0.1\ \mathrm{V}$
across the three step sizes, which is the property that was violated.

**One deliberate cost.** A run with no switching now takes three backward-Euler steps at the
start instead of one. `rules_cli`'s reversed-inductor fixture pinned `-4.3831 A`, which became
`-4.3829 A` against an analytic $-4.3835\ \mathrm{A}$; it now pins the sign and magnitude rather
than the integrator's fourth decimal, which is what that test is about.

**Verification.** `cargo fmt --all -- --check`, `cargo clippy --all-targets -- -D warnings`,
`cargo test --workspace`, `cargo doc --workspace --no-deps`, `mdbook build book/dev-guide/`.

## 2026-11-25 17:20 — A signal now says what kind of quantity it is

Issue #115: every vector this solver wrote had `{"unit": "", "quantity": "", "analysis": ""}` in
the `.gsim_samples` footer. The fields existed and the writer had nothing to put in them, so
every consumer guessed, and the guess everyone reaches for — `V(` is volts, `I(` is amperes — is
wrong for exactly the case that matters: a duty cycle of 0.42 reaches a plot as 0.42 volts.

**What was picked, and what was not.** The issue offered two encodings. Encoding the nature *in
the name* (a suffix, a prefix, a namespace) travels through every format for free, including a
CSV header someone opens in a spreadsheet — and breaks `kind=measure`, every script and every
`out=` reference that exists, which is the one thing the issue said must not break. Rejected.
Carrying it *beside* the name keeps names byte-identical, and the container's `VectorMeta`
already has the fields. Taken.

The CSV's optional second header line was the other half of that option, and it is not here. A
second header line is *data* to every plain CSV reader, including this repo's own tests and its
`kind=measure` evaluator; "a plain CSV reader will ignore it" is not true of any reader. So the
CSV is unchanged and the convention says so explicitly, rather than leaving it as an omission
someone will later try to fill.

**The rule that does the work** is that an empty `unit` means *not known* and never
*dimensionless*. A dimensionless value says so through `quantity=signal`, which is a positive
statement — this is a signal-flow value, not a potential — rather than a shrug. That is what lets
a consumer tell a duty cycle from a voltage without a second map, which is the issue's own "done
when".

**Nothing is inferred from a name's spelling.** A column's quantity comes from what it is in the
run: the sweep axis, an MNA unknown (and `general-mna` writes which kind it generated into the
name, one `V(...)` per node then one `I(...)` per branch — reading that is reading a name this
toolchain wrote to a fixed shape, and position establishes it is an unknown at all before the
prefix is looked at), or a block's output. Two block kinds have a unit because the netlist fixes
it: `kind=phys2sig` names the node or branch it reads, `kind=sig2phys` declares the domain it
drives. Every other block output is `signal` with no unit.

`raw_format::variable_type` was the same guess living in this repo already — it read a name
prefix and labelled every block output `voltage`. The rawfile still writes `voltage` there,
because the format has no generic type and the readers reject an invented one, but it now derives
it from the classification instead of the spelling, and the convention records that as the one
place it is knowingly lossy.

**The compiler's half.** The solver cannot know that a node was created to carry a signal-flow
value; that is the compiler's knowledge and it is discarded when the netlist is written. The ask
is `GLODI-Engineering/gsim-core#77`, and it is to use the grammar rather than extend it: emit a
signal-flow wire as a block output (whose nature then travels for free), and emit a crossing as
`sig2phys`/`phys2sig` (after which the node really is a potential). A grammar-level node-domain
marker is the fallback if some construct genuinely cannot be expressed either way, and that wants
specifying with whoever reads it rather than guessed at from here.

**Verification.** `cargo fmt --all -- --check`, `cargo clippy --all-targets -- -D warnings`,
`cargo test --workspace`, `cargo test --workspace --release -- --test-threads=1`,
`cargo doc --workspace --no-deps`, `mdbook build book/user-guide/` and `book/dev-guide/`,
`python3 scripts/generate-llms-txt.py`.

## 2026-11-26 02:41 — The ringing detector could not see an oscillation about a rail

`#116`. `is_ringing` tested the *sign of the raw unknown*: the outer two of three consecutive
samples sharing a sign with the middle one opposing it. That is a test for an oscillation that
straddles zero, and nothing else. A switching node ringing $\pm50\text{V}$ about a
$400\text{V}$ rail gives three positive samples and was invisible to it however badly it rang —
which is the ordinary case in a converter, not an exotic one. `#113` found it in the field: a
node rang about its $400\text{V}$ rail tens of volts past its own body-diode clamp and the
backstop never fired. `#113` removed the *excitation*; the detector stayed blind.

**Reproduced before touching it.** Seven cases written as plain sample sequences
(`ringing_detector_tests` in `lib.rs`). Two failed on `main`: the $400\text{V}$-rail Nyquist
oscillation `[450.0, 351.0, 448.02, 352.94]`, and a current ringing about $2\times10^{-10}$ —
the latter because `NOISE_FLOOR = 1e-9` was an *absolute* threshold applied to a vector whose
rows are volts in one place and amps in another, so it discarded that unknown for no reason
other than its unit.

**The fix is on the increments, and needs four samples.** $d_1 = a - w$, $d_2 = b - a$,
$d_3 = c - b$, flagged when the signs alternate *twice in a row*, the magnitudes do not shrink
(each $\ge 0.9$ of the one before), and $|d_2|$ is at least $10^{-6}$ of the largest of the four
samples. Both surviving thresholds are dimensionless ratios, so neither depends on a unit or on
$\Delta t$ — the absolute floor is gone rather than retuned.

**Why not three samples, measured rather than asserted.** The obvious repair is the same two
conditions on $d_1$ and $d_2$ alone. It does not work: at a smooth maximum the two increments
are also opposed and also equal in magnitude, so no magnitude ratio separates them, and the
detector then falls back at every extremum of every oscillating quantity. Installing exactly
that version against `tests/ringing_about_a_rail.rs` — a lossless $LC$ tank seeded off
equilibrium so it rings about a $400\text{V}$ rail and never crosses zero, at
$\Delta t = T/33$ — lost **69.4% of the waveform's amplitude over five cycles** and gave a
convergence ratio of **1.0** where second order is 4.0. Those two numbers are what the fourth
sample buys, and that test file is what holds the other direction shut.

**What it cost.** A third history vector, `x_prev3`, through all five transient loops and into
`checkpoint::Checkpoint`. A resumed run must carry it or its first steps would decide
differently from the uninterrupted run's, which is the bit-identity contract, so
`FORMAT_VERSION` went $1 \to 2$; an older file is refused up front by name, which
`from_bytes` already did.

**Reaching users needs a release.** The detector lives in `dae-runtime`, so every consumer —
the CLI, `gsim-core`, the editor — gets the old behaviour until this repository publishes.

**Verification.** `cargo fmt --all -- --check`, `cargo clippy --all-targets -- -D warnings`,
`cargo test --workspace` (76 binaries, 0 failures), `cargo doc --no-deps`,
`mdbook build book/dev-guide/`, `python3 scripts/generate-llms-txt.py`.

## 2026-11-26 03:00 — The sentences written for users were dead code; `Debug` was reaching them

`dae_message` in the CLI handled exactly one `DaeError` variant and sent every other one through
`format!("{other:?}")`. So what a user actually saw on a failed run was the `Debug` derive of a
Rust enum, and every `Display` impl in `cscript-ffi`, `pyblock-ffi`, `octave-ffi` — carefully
written, each one a sentence — was unreachable from the binary. Measured before the change, on
this tree, with a generic RC low-pass feeding one code block:

```text
error: CScript(Load { path: "./gain.so", message: "dlopen failed" })
error: Octave(NotFound { message: "No such file or directory (os error 2)" })
error: PythonSupportNotCompiledIn { block_name: "G1" }
```

The third is the worst of them: a power-electronics engineer is shown a Rust struct literal, and
the one thing they need — that this binary was built without `--features python` — is nowhere in
it. The second is information thrown away on purpose by accident: `OctaveError::NotFound`'s own
`Display` already said *"could not start octave-cli (is it installed and on PATH?)"*, and the CLI
never called it.

**`DaeError` now has a `Display` impl with an arm per variant and no wildcard**, so a new variant
is a compile error until its sentence is written. That is the guard; the test only checks that
the sentences read as sentences (no `{` anywhere in a rendered error). The three FFI-wrapping
variants delegate to the crate's own `Display`, which is what those impls were for.

**The CLI keeps the variant name in front**, as `CScript(Load): <sentence>`. That is not
decoration: this repo's own `doc-verify` scripts and CLI tests grep stderr for the variant name,
and the *inner* name (`MissingSymbol`) is grepped for as often as the outer one, so the prefix
carries both levels. It is read off the `Debug` derive rather than from a second exhaustive match,
which could only drift.

**`CScriptError::Load` threw away `dlerror`,** and this was not the `Debug`/`Display` bug — it was
one layer below it. `libloading::Error`'s own `Display` is the bare phrase `dlopen failed`; the
platform text lives in its `source()`. So `message: "dlopen failed"` was *already* the `Display`,
and the book had a whole section (`cscript.md`, "The error does not say why") documenting the
loss. Walking the source chain fixes it, and that section now says the opposite:

```text
error: CScript(Load): failed to load C-script library ./gain.so: dlopen failed: ./gain.so: \
cannot open shared object file: No such file or directory
```

`cannot open shared object file` and `undefined symbol: foo` are different problems with
different fixes, and a user shown only `dlopen failed` goes and rebuilds a library that is
already correct.

**One coupling worth recording.** Four components' `## Errors` claims — `gain`, `sum`,
`product`, `mathfn` — document `VectorSignalSizeMismatch { block: "A", expected: 2, got: 3 }`
verbatim, and those doc comments live on `general-mna`'s `BlockKind`, a read-only sibling
repository here. The fragment `expected: 2, got: 3` is therefore kept verbatim inside the new
sentence, with a comment in the code saying why. The brace spelling in the generated
`component-reference.md` is now stale and wants a `general-mna` change to match; that is filed
rather than done here.

**Verification.** `cargo fmt --all -- --check`, `cargo clippy --all-targets -- -D warnings`,
`cargo test --workspace`, `cargo doc --no-deps`, `scripts/style-guard.sh`, every
`doc-verify/*/test_*.py` against a `--features python` release build, and
`python3 scripts/generate-llms-txt.py`.

## 2026-11-26 04:40 — `lib=` was a literal filename, so a netlist was the one platform-specific thing in a deck

`lib=` went straight to the loader. No suffix was appended and none was tried, so `lib=./ctrl.so`
loads on Linux and fails on macOS and Windows: the same netlist, the same source, the same
block, a build artifact with a different name. Every *other* parameter in a netlist is
platform-neutral, and the symptom on the other machine said nothing about the name being the
problem — so the next move is to rebuild a library that is already there under a different
extension.

A `lib=` that already ends in `.so`, `.dylib` or `.dll` now resolves to **one candidate: itself**,
so no existing netlist changes behaviour at all. A `lib=` without a library suffix is a **stem**:

| `lib=./ctrl` | in order |
| --- | --- |
| Linux/ELF | `./libctrl.so`, `./ctrl.so` |
| macOS | `./libctrl.dylib`, `./ctrl.dylib` |
| Windows | `./ctrl.dll`, `./libctrl.dll` |

Both spellings per platform, because both are in real projects: `libctrl.so` is the toolchain
default for `-o libctrl.so`, and `ctrl.so` is what people type.

**`LibraryFamily` is a parameter, not a `cfg!`.** The whole claim is that a netlist written on
one platform loads on the others, and that cannot be asserted from one of them, so
`library_candidates(path, family)` is a pure function and the test pins all three lists on
whatever machine runs it. The `cfg!` lives in one place, `LibraryFamily::host()`.

`file_name`, not `file_stem`, when building a candidate: a stem may legitimately contain a dot
(`ctrl.v2`) and nothing should silently truncate at it. A bare name with no separator stays bare,
so the loader's own library-path search still applies to it exactly as documented.

When nothing loads, the error lists every path tried (`CScriptError::LoadNoCandidate`), because
"I looked for these two and found neither" is a different message from "this one file would not
load". A single candidate — the netlist naming a library outright — still returns the ordinary
`Load` with the loader's own reason, unchanged.

**What is deliberately not done.** `general-simulator-gui-for-vscode`'s
`docs/specs/code-blocks-vscode-integration.md` §6 asks whether the suffix question belongs to a
new, explicitly platform-neutral parameter instead. It probably does, and it is a `gsim-core`
registry change that wants to land with that repository's `source=` parameter rather than as a
third spelling invented here. This is the backward-compatible half, and it is enough to make a
deck portable today.

**Verification.** `cargo fmt --all -- --check`, `cargo clippy --all-targets -- -D warnings`,
`cargo test --workspace`, `cargo doc --no-deps`, `scripts/style-guard.sh`,
`python3 scripts/generate-llms-txt.py`. The end-to-end CLI test was watched failing with stem

## 2026-11-26 06:20 — one question, three vocabularies: where did the code block fail

A code block's error said where it happened in one language, half-said it in a second and never
said it in the third, so a front end could not route any of them to a line. Measured before the
change, the same failure (reference an undefined name) in each language:

| language | what came back | file? | line? | column? |
| --- | --- | --- | --- | --- |
| Octave, runtime | `'nosuchvariable' undefined near line 3, column 13` | no | **yes** | **yes** |
| Octave, parse | `syntax error near line 2, column 12 in file /…/dbl_bad.m` | **yes** | **yes** | **yes** |
| Python, runtime | `NameError: name 'undefined_name' is not defined` | from the error's `path` | **no** | no |
| Python, load | `SyntaxError: invalid syntax (ctrl_syn.py, line 1)` | yes, by accident | yes, by accident | no |
| C, runtime | nothing | no | no | no |

Octave was the richest and it was accidental; Python was the deliberate loss; C has no channel
at all.

**Python.** `py_traceback` was `err.to_string()`, which for a `NameError` is one sentence with no
frames. Nothing was missing: `exec_fresh_module` already passes the user's real path as the code
object's filename, so every frame reads `File "<their own file>", line N, in output`. The
traceback was simply never formatted. Now:

```text
error: PyBlock(Exception): Python block ./ctrl_bad.py raised in `output`: Traceback (most recent call last):
  File "./ctrl_bad.py", line 10, in output
    return 2.0 * u + undefined_name
                     ^^^^^^^^^^^^^^
NameError: name 'undefined_name' is not defined
```

Both halves are returned, for different readers: the text for a person reading an output panel,
the fields for a front end putting a diagnostic on a line, which should not have to regex a
human string. Python's own `traceback` module does the work -- `format_exception` for the text,
`extract_tb` for the frames -- rather than a hand-walk of the frame objects. A `SyntaxError` has
no traceback into the file that did not compile, so its position comes off the exception value's
own `filename`/`lineno`.

**Octave.** The position was always in `err.message`; the *file* was in `err.stack`, which the
`catch` wrapper read and discarded. The `catch` branch now prints an
`ERROR-AT: <file>|<line>|<column>` line after the `ERROR: ` line -- second on purpose, so every
reader that checks `lines.first()` for the `ERROR: ` prefix and returns early is unaffected by
the extra line. There were six copies of that one `printf`; there is now one `catch_branch`.

The part worth remembering is **why both sources are needed**, which a single measurement
settles:

- a *runtime* error: `err.stack(1)` is the failing function (`dbl_bad.m`, line 3, column 3) and
  the message has no file but the precise column (13, where the identifier is);
- a *parse* error: the message carries `in file /…/syn.m` and the position, and `err.stack(1)`
  is the **caller** (`exp2.m`).

So the message wins for the position, the message wins for the file when it names one, and the
stack's first frame fills the file in otherwise. Taking the file from the stack unconditionally
would name the wrong file for every parse error.

The sentence names the file now too, because with several blocks sharing one session "near line
3" does not say which `.m` file line 3 is in.

**C has no runtime error channel and will not get one.** `cscript_output` returns `void`. Adding
a return code would change the call signature every existing block declares, which is the one
thing in this contract that cannot be changed compatibly. So a C block's failures divide into
build (a file and a line, belonging to whoever ran the compiler), load (names the library and
the block, which is all that is knowable) and runtime (invisible). Written into `cscript-ffi`'s
module doc, and `no_c_block_failure_claims_a_location` is the test that stops someone
"improving" the mapping later by pointing a diagnostic at line 1 of a `.c` file nobody read.

**One shape, at the boundary rather than in a shared crate.** `dae_runtime::CodeLocation` plus
`DaeError::code_location()` is the single answer a front end reads. The per-language structs
stay in their own crates: `octave-ffi` and `pyblock-ffi` have no common dependency, and
inventing a crate to share three small structs would cost more than the duplication. What
matters is that a caller asks one question once, and that is what this gives.

`python3 scripts/generate-llms-txt.py`. A test per language asserts the reported line equals the

## 2026-11-26 05:40 — the ABI is published as a header, because a hand-typed prototype cannot be checked

Nobody includes an engine-provided header for a `cscript` block, because there was none. Every
block retypes the `cscript_*` prototypes by hand, and that is the one mistake in this contract
that neither a compiler nor a test run on this platform can catch.

Measured, before anything was written: the plausible wrong guess
`void cscript_output(void *state, double t, double dt, const double *in, int in_len, double *out, int out_len)`
compiled with `-Wall -Wextra` (no diagnostics) and run against a generic RC low-pass gives
numbers identical, to the last digit, to the correct declaration. On x86-64 System V,
integer/pointer and floating-point arguments come from separate register files, so counting only
the integer class both signatures put `state` 1st, `in` 2nd, `in_len` 3rd and `out` 4th, and
`dt` is the first float in both. Windows x64 assigns the first four arguments to RCX, RDX, R8,
R9 positionally regardless of class, so there the engine's `in` pointer lands where the callee
reads `dt` and the callee builds its `in` pointer out of the integer `in_len`.

`crates/cscript-ffi/include/gsim_cscript.h` publishes the whole contract -- every required and
optional symbol, each with what its absence means -- already wrapped in `extern "C"` for C++.
`cscript_ffi::header()` returns its bytes, so a front end scaffolding a C block can write the
real header beside the source it creates instead of keeping its own copy of the prototypes.

**The test does not compare text, and that is the point.** A header that merely looks like the
contract is worth *less* than no header, because it moves the hand-typed prototype into this
repository and stops anyone questioning it. `tests/published_header.rs` compiles a block that
includes the header and defines nothing else -- so every prototype comes from the header -- with
`-Wall -Wextra -Werror`, and then loads and calls it through the real `CScriptRegistry`. A C
compiler will not let a definition disagree with a prior declaration in the same translation
unit, so the block's `cscript_output` *is* the header's; and the loader calling it correctly
means the header's *is* the engine's. Verified by corrupting the header to the wrong signature:
three of the four tests fail with `conflicting types for 'cscript_output'`.

One test earns its place beyond that. `the_header_puts_dt_and_the_input_where_the_engine_puts_them`
returns `dt` itself and `in[0] + in_len`, so a declaration that crossed a float with a pointer
would come back wrong in both columns rather than being ignored. On x86-64 it cannot cross them;
this is the assertion that would fire on Windows.

**Verification.** `cargo fmt --all -- --check`, `cargo clippy --all-targets -- -D warnings`,
`cargo test --workspace`, `cargo doc --no-deps`, `scripts/style-guard.sh`,

## 2026-11-26 04:10 — A Python block could not import the module beside it, and making it able to created a second silent wrong answer

`python ctrl.py` puts the script's own directory first on `sys.path`. This crate execs a block's
source instead of launching it, so nothing told the import machinery where the file lives:

```text
error: PyBlock(Load { path: "./ctrl_sib.py", message: "ModuleNotFoundError: No module named 'helper'" })
```

for a `helper.py` sitting right next to the block. That is the one thing anyone does after
writing a second block — factor the shared part into a file in the same directory — and it was
the one place it did not work.

The directory is derivable from the block's own `path=`, so asking a user to restate it in
`PYTHONPATH` was asking them to repeat what the netlist already carries, and `PYTHONPATH` is
process-wide so it could not serve two blocks in two directories without enumerating both.

**Appended, not prepended.** A block's own file is not a program the user launched; it is a file
the engine was pointed at. Prepending would let a sibling named `json.py` shadow the standard
library's `json` for the whole process. There is a fixture for exactly that — a block beside a
`json.py` whose `output` asserts `json.dumps([1]) == "[1]"`.

**And then the interesting part.** Appending each block's directory makes a *second* silent wrong
answer available, which the issue's own "done when" asked for without naming: *"a block in
directory A and a block in directory B each import their own sibling in one netlist."* With
differently-named siblings that now works. With **same-named** siblings it cannot: `sys.modules`
is process-wide, the first `import helper` in a run wins, and every later one returns that same
module. Two blocks each holding their own `helper.py` would both compute with the first one's
constants — a block silently running another block's control law, which is the same class of
failure as `octfunc`'s `path=` and would have been *created* by this change.

So it is refused, at construction, naming both files
(`PyBlockError::SiblingImportShadowed`). The check is exact rather than conservative, and the
distinction is the whole design:

- it fires only when this block's own directory genuinely offers a module of that name, **and**
- the module that won came from a directory this process registered for *another block*.

The standard library or an installed package winning is the intended consequence of appending,
not a collision, so the `json.py` fixture passes rather than being refused. The set of block
directories is process-wide (a `OnceLock<Mutex<BTreeSet<PathBuf>>>`), which is honest: `sys.path`
and `sys.modules` are themselves process-wide, so "which directories are block directories" is a
property of the process and not of a registry.

One limitation, stated rather than papered over: the check sees `import helper`, which binds a
module object in the block's namespace. `from helper import K` binds `K` and leaves nothing to
inspect.

**Checked at construction only, never in `try_clone`.** A clone re-execs the same source in the
same process, so its imports come from `sys.modules` and can only agree with what construction
already passed — and `try_clone` runs once per rejected adaptive trial step, which is not a place
for a filesystem probe.

**Verification.** `cargo fmt --all -- --check`, `cargo clippy --all-targets -- -D warnings` and
`--features python`, `cargo test --workspace` and `--features python`, `cargo doc --no-deps`,
`scripts/style-guard.sh`. The end-to-end CLI test was watched failing with the `sys.path` append
temporarily commented out, not merely written afterwards.
## 2026-11-26 09:10 — the binary can now say whether it can run a Python block

`kind=pyblock` and `kind=pyfunc` need a `--features python` build, and the release workflow
deliberately does not publish one — linking against one specific libpython would make it a worse
download, and its own header comment says so. So **the binary a user downloads cannot run a
Python block at all**, and neither can one built with the `cargo build --release -p
general-simulator-cli` line a front end's setting description gives. Both documented ways of
getting an engine silently exclude the two most-used extensibility blocks.

Until now the only way to discover that was to draw a sheet, press Run, and read
`PythonSupportNotCompiledIn`.

**`--help` cannot answer it**, which is the part worth stating: its NOTES section says
*"kind=pyblock and kind=pyfunc need a `--features python` build of this binary"* whatever this
binary is. A front end scraping that text learns nothing about the binary in front of it, so
screen-scraping is not a cheaper version of this flag — it is a wrong answer.

```console
$ general-simulator --capabilities
program=general-simulator
version=0.9.0
python=no          # `yes` on a --features python build; verified both ways
octave=subprocess
cscript=load-only
```

**`key=value`, one per line, nothing else** — no banner, no prose, no blanks. A front end never
has to regex text a reword would break, a shell can read it with one `sed`, and a new key can be
added without breaking a reader that does not know it. `version_and_help_cli.rs` pins the
*shape* as well as the keys, so a future banner line is a failing test.

**The three languages answer three different kinds of question, and the values say which kind.**
That is the design, not decoration:

- `python=yes|no` is a property of this **build**. Nothing but a rebuild changes it, and the test
  asserts it against `cfg!(feature = "python")` so it cannot drift from the build it describes.
- `octave=subprocess` is a property of the **design**: `octave-ffi` spawns `octave-cli` and never
  links against Octave, so this binary is always able to *try*. Whether that program is on `PATH`
  is a question about the machine, which no build can answer — so this says how Octave is
  reached rather than claiming it is available. A flag that promised availability here would be
  lying on every machine without Octave.
- `cscript=load-only` is a property of the **contract**: this binary loads a shared library and
  never invokes a compiler.

Asked for by `GLODI-Engineering/omni-schematics#238`, whose preflight needs to tell a user what
to install *before* the run rather than after it, and which explicitly preferred this to
screen-scraping `--help`.

**Verification.** `cargo fmt --all -- --check`, `cargo clippy --all-targets -- -D warnings`,
`cargo test --workspace` and `--features python` (the capability test runs under both and asserts
the opposite answer each time), `cargo doc --no-deps`, `scripts/style-guard.sh`,
`python3 scripts/generate-llms-txt.py`.
