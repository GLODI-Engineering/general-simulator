## 2026-11-06 06:13 — `#21` is wrong; what is real is the `phys2sig` sampling delay

**Asked:** solve the open bugs. `#21` claimed *every* CSV row's values are one $\Delta t$ behind
that row's own timestamp, which would bias every windowed measurement in the project.

**Found: the claim does not reproduce, and I filed it.** Measured, not argued:

- A 50 Hz `SIN()` source run at `--dt 1e-4` gives `V(vac_node)` equal to
  $A\sin(2\pi f t)$ at the row's own stamp to full printed precision — not
  $A\sin(2\pi f (t-\Delta t))$, which the issue asserted matched "to every printed digit".
- The same sinusoid as a `kind=sinwave` *block* agrees with the source column row for row, so
  the circuit solve and the block graph share the same stamp.
- The `pulsewave` edge that prompted the report (`pw=6e-6`, `--dt 1e-7`) is correct. The last
  high row is stamped `5.999999999999995e-6` — accumulated float addition, *below* 6 µs, where
  the gate is genuinely still high. Reading that as "6e-06" is what produced the report. It is
  a one-line mistake that a glance at the printed digits does not catch.

**What is real, and narrower.** `kind=phys2sig` reports the circuit as of $t-\Delta t$, and `0`
in the first row, because `evaluate_blocks` is handed `point_prev` — the block graph must be
evaluated before the circuit is solved, since a block's output can decide a gate state or a
source magnitude for the step about to be solved. Deliberate, and already documented in
`book/dev-guide/src/block-graph-descriptor.md`, `docs/architecture.md`, and the module doc
comment. Already asserted per-step by `crates/dae-runtime/tests/phys2sig_block.rs`.

So the behaviour was tested and designed; the gap was that **no user-facing page said it, and
the component reference said the opposite** — "`PROBE1` tracking `V(out)` exactly", with
`doc-verify/phys2sig` asserting that on the *last* row of an already-settled divider, where it
is true. A settled circuit hides the delay after row one.

**Changed.**

- `crates/dae-runtime/src/block_graph.rs`: the `Phys2Sig` match arm is now a named, documented
  `phys2sig_value`, carrying a `<!-- doc-ref: phys2sig -->` implementation note. That tag is how
  this repo adds to a component entry whose primary doc comment lives in `general-mna`, which is
  a read-only path dependency here.
- `book/user-guide/src/reading-output.md`: new "What time a row's values belong to" — the first
  row is $t=\Delta t$ (which `measurements.md` already linked here for and this page did not
  have), every column is the row's own $t$, and the one `phys2sig` exception with its verified
  output.
- `book/user-guide/src/signals.md`: its `prev:PROBE` example already *showed* `PROBE=0` while
  `V(b)=2.5` and said nothing about it. It now says `DELAY` ends up two steps behind the
  circuit, and which step belongs to which mechanism.
- `crates/general-simulator-cli/tests/csv_row_time_alignment.rs` (new, 4 tests): pins both
  halves — no global offset, and the probe's offset is exactly one step — so a fix aimed at
  either claim cannot silently break the other.
- `doc-verify/phys2sig`: runs the same netlist a second time at a coarse `dt` and asserts the
  per-row relation, instead of only the settled last row.
- `docs/gotchas/GOTCHA-002`: both traps that let this survive — the settled-circuit check, and
  the fact that near a sinusoid's peak $\sin(t)\approx\sin(t-\Delta t)$ so a spot check cannot
  tell a one-step shift from none. The second is exactly what produced the wrong diagnosis.

**Not changed.** The delay itself. `docs/architecture.md` records it as a deliberate choice and
`book/dev-guide/src/design-decisions.md` names what would have to be true to revisit it; that is
a design question, not a bug fix. `general-mna`'s own `Phys2Sig` doc comment still says the
example "tracks `V(out)` exactly" — correcting it there needs explicit confirmation first
(`AGENTS.md`, project boundaries), so the implementation note names the caveat directly below it
in the generated entry.
